# 当前系统的四条改进主线：原系统归属与新增机制核对

核对日期：2026-09-17；对象：当前工作树中的 **hybrid_sssp 动态 SSSP 系统**，包括未提交实现；原版为用户指定的 `/home/wangshaoyan/proJect/C-GpuStreamGraph`，源码基线 `7ffcb29`。

**修订结论：我们没有提出 GPU 增量图计算、GPU hot 子图缓存或 PCIe Zero-Copy。它们都是原系统 Grapin 的基础。** 从 72 项工作记录中，可整理出四条实际改进：①隔离 source 更新并共享有效变更、稀疏发布；②删除后独立恢复与精确活动源闭包；③发布时修补 resident 邻接并条件跳过缓存维护链；④长传播下的有序删除/插入执行。其中③按原迭代定位属于配套性能机制，不应把整个 hot-cache 框架包装成我们的独立算法贡献。

本文先划归属，再按“原来如何做 → 我们改哪里 → 当前怎么执行 → 证据边界”说明。四条是写作组织，不是四项已证明全球首次提出的算法；末尾仍保留全部 72 项的归属，不因压缩遗漏研发工作。

**两个最容易混淆的“chunk”：** 原论文的 GPU cache chunk 是对紧凑缓存边数组的逻辑分块；我们的 CPU source-local chunk 是权威拓扑中按 source 独立分配的邻接块。原 CPU PMA 本来也保持单个 source 邻接连续，因此新增点是**跨 source 更新隔离及其发布契约**，不是“第一次让邻接连续”或“第一次分块”。

### 1.2 当前一批更新究竟如何执行

先约定：**source** 是一条边的起点；**affected** 是删除导致需要恢复距离的顶点集合；**incoming** 是这些顶点仍存在的入边来源；**descriptor** 是 GPU 定位某 source 邻接的地址/degree 元数据；**resident** 是已有有效 GPU cache 内容的顶点。CPU 负责权威拓扑和反向索引，GPU 负责主要距离传播——前一种 CPU 工作不是已退休的 CPU propagation owner。

| 顺序 | 当前动作与输入/输出 | 对应新增机制 |
|---|---|---|
| 1. 组织更新 | CPU 将混合批次按 source 分组一次，提供删除、插入两个视图，此时不提前应用插入 | ①共享分组 |
| 2. 识别失效 | GPU 在旧图上从删除依赖出发，产生 compact affected 队列并传播失效，再将受影响距离重置 | ②将原有失效过程改为直接消费事件队列 |
| 3. 删除并恢复 | CPU 应用实际删除、提交 reverse 变更，只物化 affected 顶点的 incoming；GPU 根据删除后图恢复距离直到收敛 | ①有效删除契约＋②独立删除恢复；④可替换其执行顺序 |
| 4. 插入并发布 | CPU 应用新增边、更新 reverse，合并两 phase 的 changed sources；GPU scatter 最终 descriptor，并修补对应 resident cache 内容 | ①稀疏发布＋③局部修补 |
| 5. 启动插入传播 | GPU 只松弛本批新增边，把真正改善的 destination 放入 source 队列，在设备内传播到队列为空 | ②精确 source 闭包；④可启用距离窗口 |
| 6. 维护热数据 | 继续原有 hotness/候选选择；验证目标 resident 集合，需要刷新才调用 eviction/compact/load | ③跳过无必要的常规维护链 |

调用依据：[SSSP 入口](../samples/hybrid_sssp/hybrid_sssp.cu) 的批次循环，以及[框架](../include/framework/framework.cuh) 的 `del_edge/update_tree_del/update_tree_add`。删除恢复使用 CPU 维护的删除后 incoming；最终 GPU descriptor/cache 发布位于插入侧，**不是每个 phase 各发布一个完整 GPU 图**。I20 共享的是规划数据，不是把删除、插入两次收敛合成最终态事务。

也不能把原来的 cache/Zero-Copy 二选一概括套到每个新 kernel：当前 `RunExactGpuClosure` 调用 `graph.edge_dest`，实际读取 mapped `chunk_slabs_`；普通 affected repair 读取显式传入 GPU 的 incoming 数组，有序删除再使用局部 outgoing CSR。主线③确认的是缓存**维护成本**的变化，不能仅凭系统保留了 cache 就推断这些闭包获得了新的缓存命中收益。

### 1.3 主路径与显式模式

| 配置/机制 | 当前事实 |
|---|---|
| CPU 传播 owner | `sssp_cpu_partition_capacity=0`、domain map 默认空；遗留分支仍在，不列为当前贡献 |
| 普通传播 | 默认删除为 affected GPU pull，插入为 block/source cooperative closure；删除仍有 host 逐轮控制 |
| `CG_ORDERED_REPAIR=1` | 同时选择有序删除、强制有序插入，优先于旧插入 schedule；人工启用，不是自动识别器 |

| reverse 分片、publication 合并 | 默认 shards=1、merge 关闭；reverse64 和 `CG_MERGE_PUBLICATION_SOURCES=1` 是显式且有内部收益证据的配置 |

## 二、四条改进主线：只认领真实增量

### 主线一：隔离 source 更新，以一份有效变更贯通双向维护与稀疏发布

**原系统与改动位置。** 原 CPU PMA 中一个 source 扩容可能触发邻域 rebalance，搬动其他 source 的邻接并改变它们的 descriptor。原 `update_tree_add → ReloadAllocator → AllocateDevMirror_node_update` 随后复制 `(V+1)` 个 descriptor。因此问题不只是“传得太多”：只把 memcpy 改成 touched-source 列表并不安全，因为未被请求触及的 source 也可能被 PMA 搬动。

**我们的完整处理链：**

1. **先隔离存储影响。** 用 source-local 连续 chunk 替代运行期全局 PMA 更新；扩容只给该 source 分配新块，其他 source 地址不变。主存映射访问沿用原有技术，新增的是分配/更新边界。
2. **按 source 规划实际操作。** 一次稳定分组供两个 phase 使用；匹配实际存在的删除 occurrence，计算最终 degree 和容量。先容量预检，再由固定 worker 池并行 compact/append/rewrite；分配及 epoch/retire 管理保留必要串行。它减少逐条删除搬移和跨 source relocation，并非保证完全不扫描旧邻接。
3. **把“请求”变成“实际变更”。** forward 产生带正负重数的 `EffectiveEdgeDelta`。reverse 先 Prepare 排序、归约及所需槽位，成功后才允许 forward 可见修改，再以预备好的向量 swap Commit；只有真正 changed source 进入发布列表，避免缺失删除令 forward/reverse 分歧。
4. **复用表示和顺序。** reverse 维护 CPU sorted incoming base＋signed overlay；已有 source 顺序供 destination 排序复用，预建槽位后并行 merge。显式 reverse64 分散 map 预建；large 模式共享单份重型 plan 并 move 有效记录缓冲；显式 publication merge 线性合并两 phase 的有序 source 列表。这些是同一数据流的实现细化。
5. **最后稀疏发布。** 每个 changed source 传24-byte patch，scatter 到兼容 GPU descriptor；stream event 保证发布先于消费者读，旧块在相应读取完成后才回收。发布 staging/event 复用，完整邻接 digest 仅在检查模式执行。

**小例子。** source `s` 原邻接为 `[a,a,b]`，收到“删 `a` 三次、加 `c` 一次”。删除只成功两次，reverse 收到 `(s,a,-2)`，删除后图是 `[b]`；该图完成距离恢复后才应用 `(s,c,+1)`。最终只发布 `s` 的新地址/degree，其他 source 不因本次扩容改变。例子说明有效重数与 phase 可见性，**不把 occurrence 本身声称为全新图语义**。

**归并与依据。** C1–C3/D1–D3 建立隔离与发布，I5–I10 完成并行/可见性/回收，I14 统一有效更新，E4-R2/B5 改善 reverse，I20/I24 继续去重复物化和排序；合为一个系统机制。阶段来由见[主计划 C/D、I14、E4-R2](cggraph_cpu_gpu_dev_implementation_plan.md)、[I20共享规划](subiteration_file/i20_shared_plan_20260915.md)、[I24发布合并](subiteration_file/i24_tw10m_publication_20260917.md)。

代码：[SourceLocalChunkStore](../include/groute/graphs/source_local_chunk_store.h) 的 `ApplyMutationPhase/BuildDeletionPlan/EnsureAllocationsFit/ReclaimThrough`；[GroupedUpdateBatch](../include/framework/effective_update_batch.h)；[DynamicReverseIndex](../include/framework/dynamic_reverse_index.h) 的 `Prepare/Commit/MergeIncoming`；[排序](../include/framework/effective_delta_sort.h)、[发布集合](../include/framework/publication_sources.h)；[GPU发布](../include/groute/graphs/csr_graph.cuh) 的 `PublishSparse/WaitForSparsePublication/CompleteSparsePublication`。

**可以认领的范围。** source 更新隔离、有效变更共享与稀疏发布的组合，而非 pinned/Zero-Copy/连续邻接/CPU维护本身。D1 删除额外 `24×V` extended descriptor 是消除我们 C3 中间版本引入的开销，**不能写成相对原版直接节省24×V**。实际 patch payload 跟 changed sources 走，预留容量却按最大 batch；仍有 pinned 内存、chunk 容量放大、全图初始化、CPU reverse base 和长期 overlay 成本，未交付长期 base compaction 或跨批双版本流水。

### 主线二：删除后独立恢复，再以精确活动源替代全点插入启动

**原系统与改动位置。** GPU 增量修复/传播是继承基础：原 `update_tree_del` 已从 parent 依赖出发重置并传播失效，原论文也已区分结果修正与迭代计算。但本地原版 SSSP 的 `update_tree_add` 在物理加/删和 reload 后调用 `RebuildWorklist_AllVertices → ExecutePolicy_All`，再通过 host 驱动 segment 收敛。我们改的是这条实际执行链的工作粒度与阶段契约，不能笼统写“提出GPU增量算法”。

**为何不能直接删掉全点启动。** 主计划10.8–10.9记录了直接改成 added-edge seed 后仍有可松弛边的失败：删除使原 parent 路径失效时，替代路径可能来自一个没有被新增边激活的外部顶点。只从新增边启动无法保证把这条路径找回来。因此“删除后先独立恢复”是“插入只用新增边启动”的前提；两者应合为一项，而非两个互不相关的优化。

**删除端的执行链：**

1. 在旧图上沿依赖识别失效，成功失效直接追加 compact affected 队列；每轮只消费新追加区间，而非重建所有 segment。保留 parent/tight-edge 防护，结束后重置 affected 距离。
2. CPU 物理删除并提交主线一的 reverse；只为 affected destinations 合并出当前 incoming，形成 offsets/source 数组。大集合按4096-destination tile 并行组织，再紧凑 H2D。
3. GPU 从仍有限的边界距离求替代值，并在 affected 区域迭代到不再变化；普通路径以一个 warp 合作处理一行 incoming。距离状态留在 GPU，CPU负责依赖数据准备，不承担这一闭包。

**插入端的执行链：** 完成删后 fixed point，再插入并发布拓扑 → 松弛本批新增边 → 只有实际改善的 destination 入队成为待扩展 source → 每个 source 展开邻接，成功改善生成下一波 → `(epoch,wave)` ticket 保证同一 source 每波至多调度一次，但后续波仍可再次激活 → cooperative kernel 在设备内交换双队列并判断结束。

**直观例子。** 删除 `u→v` 使 `v` 原距离失效，但图中仍有 `x→v`，且 `x` 不在本批新增边的影响范围内；先从 reverse 找到 `x→v` 恢复 `v`，后续插入才可以放心只处理新增边带来的改善。新增的是这个局部恢复与精确启动闭环，不是发现了“删除后要重算”。

**归并与依据。** 10.8–10.9/A/B1–B2 完成阶段正确性、affected 恢复和稀疏化；E4-R1 将 source 队列/终止移入设备；B5 改善 incoming 物化与归约。见[主计划相应阶段](cggraph_cpu_gpu_dev_implementation_plan.md)和[B5实现及组合实验](subiteration_file/i17b5_incoming_source_order_20260914.md)。

代码：[框架](../include/framework/framework.cuh) 的 `update_tree_del/RunGpuAffectedRepair/SeedAddedEdgeFrontier/RunExactSourceClosure/RunExactGpuClosure`；[失效 kernel](../include/framework/variants/driver.cuh)；[依赖防护](../include/framework/variants/push_functor.h)；[incoming 物化](../include/framework/dynamic_reverse_index.h) 的 `MaterializeIncoming`。独立 `ExactSourceFrontier` 是协议/测试基座，生产 GPU 使用 ticket，不是 host 类逐波调度。

**可以认领的范围。** 原有增量引擎之上的独立删除恢复、compact affected 数据流、成功事件精确入队和设备内闭包组织；不认领 DM、parent CAS、CTA/warp 或通用 frontier 思想。B1相对CPU repair、B2相对B1、B5相对内部前版的收益都不是原版消融。删除仍有全V reset和host轮间同步；传输量由 affected incoming 边数决定；插入要求 cooperative launch 且 ticket 有界。distance/存在性 tight witness 的证据不等于整个 stored-parent 树已全面封板。

### 主线三：发布时修补 resident 邻接，满足条件才跳过原有缓存维护链

**定位：配套性能机制。** 保留这项真实工作，但不作为“提出 GPU hot 子图缓存”的贡献；原 F1-C0 也将它列为支撑工程项。

**原系统与改动位置。** 原论文已经支持按 snapshot 保留热数据和按 cache chunk 局部回收。具体原版代码中，`read_del/read_add` 调用 `reset_pr_del_edges` 使 touched source 的缓存失效；批次入口随后调用 eviction/compact/load。我们的直接机会是：**顶点仍应留在 cache、邻接又可以小范围修补时，是否还需要执行整条常规维护链？** 不是把原版描述成不具备局部缓存更新。

**当前执行规则：**

1. 将 cache payload 更新放入主线一的 topology publication，同一 stream 先更新 descriptor，再处理 changed resident source。
2. 若新 degree 不超过原有效长度，复用原槽；若增长，尝试在同一 cache 分配的未用尾部放入该 source 的新邻接；失败则失效，保留正确的冷邻接访问和后续常规刷新。
3. 每次修补复制该 source 的**当前完整邻接**，不是仅发送几条增删边的 edge-delta patch；局部性是 source 粒度。
4. 继续原 hotness/排序/容量前缀选择，检查 desired 顶点全部有有效 resident 内容，且 desired 数量与已发布集合一致；成立才跳过 eviction/compact/load。首次、缺失或数量变化都执行常规维护，不据“ID相同”忽略 payload 变化。

例如一个仍属热集合的顶点删了一条边，槽位足够就直接改写其邻接；若整个 desired 集合仍有效，就不必启动回收、压缩和重新装载。顶点变冷、新顶点进入热集合或空间不足时，仍需要原有维护服务。

**归并与依据。** F1-C0 的 producer-native patch、P0 的 tail fallback、后续 refresh gate 合成一项；I15 score/ID 配对为正确性支撑。见[主计划 F1-C0/P0](cggraph_cpu_gpu_dev_implementation_plan.md)及[I15事件契约](subiteration_file/i15_event_contract.md)。代码：[GPU图适配](../include/groute/graphs/csr_graph.cuh) 的 `ReserveCachePatchOrInvalidate/PatchOrInvalidateCachedAdjacency`（由 `PublishSparse` 调用）、[RefreshGate](../include/framework/cache_refresh_gate.h)、[SSSP批次条件调用](../samples/hybrid_sssp/hybrid_sssp.cu)。

**可以认领的范围。** 在已有缓存上增加 source 发布修补和维护链跳过条件；不认领 hotness、CSR cache、chunk compaction、保留未变数据或 ZC 装载。全顶点 hotness/候选排序仍在；没有生产 weighted treap/extent allocator；尾部碎片和容量边界仍在。历史收益来自相对我们 F0-L 内部基线的维护成本降低，不能说是相对原版首次获得热子图复用收益。

### 主线四：长传播下改变服务次序，抑制重复扩边

**原系统与改动位置。** 原版已有增量松弛、工作队列与warp/block调度；这里新增的是当前系统对 pending 工作的距离次序控制。它不是把 GPU 增量算法再计一次，也不主张发明 Dijkstra、bucket 或一般 delta-stepping。

**为何需要另一种执行次序。** 精确 frontier 能排除未激活顶点，却不能阻止同一顶点被更好距离多次激活。长传播中，先传播较差距离、随后又传播更好距离，会重复扫描大量边；I22 曾试 thread/source 调度仍处理大量重复边，才转向距离窗口。

| 环节 | 有序删除 | 有序插入 |
|---|---|---|
| 准备数据 | 将 affected incoming 中的内部边转成 local outgoing CSR，以边界距离初始化 | 沿用主线二的 source 双队列与 GPU buffer |
| 本轮选择 | 从稀疏 active list 求最小 `distance/128` bucket | 求 pending 最小距离，只服务 `[min,min+127]` |
| 未选任务 | deferred 保持 pending，继续保留 | carry 到下一队列，不提前提交 value |
| 成功改善 | pending 去重，新改善继续入队 | carry 与改善事件共用 wave ticket，下一波读最新 buffer |
| 结束与成本 | 发布 affected 距离并重建其 tight parents；每轮仍回读一次 counters | 同一 cooperative kernel 内循环至队列为空；每波的最小值扫描/carry也计成本 |

I17 的控制合并将 bucket/selected count 留在设备，双队列首尾复用减少一条大队列，属于有序删除的成本优化；I22 在已有闭包上增加插入距离窗口，并用 `CG_ORDERED_REPAIR=1` 统一选择两端。**两端目标相同但实现不同：不能把插入写成已有完整物理桶，也不能把删除写成无host同步的persistent kernel。**

**归并与依据。** I17-A/B 的独立 replay、B6 的生产接线、I22 插入窗口归为一条主线。见[I17控制/队列成本](subiteration_file/i17b_gpu_cost_results.md)、[B6结果](subiteration_file/i17b6_completed_analysis.md)、[I22迭代及模式优先级](subiteration_file/i22_ordered_insertion_20260916.md)。代码：[ordered_gpu_repair.cuh](../include/framework/ordered_gpu_repair.cuh) 的 `Run/Seed/FindActiveBucket/PartitionActive/Expand/Parents`；[框架](../include/framework/framework.cuh) 的 ordered 分支和 `RunExactGpuClosure<…, true>`。

**可以认领的范围。** affected 局部有序删除、插入 carry/改善统一去重及其生产接线和成本控制；已接入但必须显式启用。收益是减少重复边松弛，不保证减少wave，I22 EU1M的wave实际增加。当前限于既定1..128正权、有限距离/ID和16-bit插入wave；删除仍有O(V) host local映射初始化及CSR转置/分配/H2D/释放。道路图有内部收益，FS/TW有序插入有回退；没有自动图类型选择器或任意权普适性结论。
