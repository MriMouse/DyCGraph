# FS/TW 10M、100M 扩展性优化可行性复核（2026-09-16）

用户要求评估是否还有优化空间、是否值得继续，以及是否可能在10M/100M超过原系统。本轮完成生产代码审计、已有日志重新分解，以及两个独立CPU机制实验；没有修改生产路径，没有启动完整GPU实验，没有生成合法100M更新数据。实验后台串行运行，均已结束。

## 结论与证据等级

- **TW10M：值得继续，存在具体而非泛泛的追平机会。** 两个机制实验的两批折算节省约1.227秒，超过I20均值到历史目标的0.573秒缺口。但折算不是整系统测量，必须集成验证。
- **FS10M：有条件值得继续，尚不能保证胜出。** 同两项折算约1.660秒，仍小于2.183秒缺口；还需从reverse排序、有效变更生成或其他准备成本中取得约0.523秒净收益。若要求比历史原版快5%，需总计削减约2.756秒，门槛更高。
- **100M：算法机制有继续扩展的理由，但目前不能判定胜负。** 只有100M记录级排序压力实验，既没有合法100M完整运行，也没有原系统100M基线；当前publication显存预留、固定chunk arena及reverse历史增长必须先处理/验证。
- 历史22组跨系统共同指纹全部不匹配，原版部分配置重复间不稳定。因此历史时间仅为研发目标线；新算法再快也不能自动恢复有效加速比。性能开发可继续，正式“战胜原系统”需同语义、同输入、同条件的结果一致性证据，不要求以重跑整个正确性矩阵作为当前优化前置。

## 2. 重新分解近期成本

从`logs/i22_scope_20260916/{tw,fs}_scaling_10000k_block/run.log`重算，两批合计秒：

| 阶段 | TW | FS | 层级 |
|---|---:|---:|---|
| mixed-source grouping | 1.692 | 1.730 | 外部准备 |
| mutation prepare | 1.549 | 1.960 | mutation子项 |
| mutation preflight | 3.208 | 4.164 | 包含reverse Prepare |
| reverse Prepare各子项合计 | 1.580 | 1.981 | preflight子项，不能再相加 |
| preflight减reverse Prepare | 1.627 | 2.183 | 未进一步独立计时的预算，不代表全部可消除 |
| reverse sort | 0.790 | 0.817 | reverse Prepare子项 |
| mutation apply | 0.840 | 0.932 | 包含reverse Commit |
| reverse Commit | 0.498 | 0.632 | apply子项 |
| repair closure | 0.415 | 0.359 | 传播部分 |

代码对应：

1. `effective_update_batch.h::GroupedUpdateBatch`串行生成12字节Record、四轮8-bit稳定radix、串行物化groups/destinations/phase indices。
2. `source_local_chunk_store.h::ApplyMutationPhase`仍创建大规模PreparedResult，串行扫描结果、生成effective与changed，并初始化逐source apply metrics；I20删掉的是第二份source规划，不是整个规划阶段。
3. `dynamic_reverse_index.h::Prepare`的过滤、排序、pending destination分组仍有串行段。64 shards只并行部分容器准备，不等于整个reverse都并行。
4. `framework.cuh`发布前仍将delete/add两个已排序changed-source列表拼接后`std::sort + unique`。这些列表分别按source有序，能保留边界后线性合并去重；必须使用实际changed列表，不能把全部touched source冒充已变更source。
5. `preflight`包含EnsureAllocationsFit、有效变更串行生成、reverse Prepare、apply metrics初始化等。现有2.183秒FS剩余预算不足以区分各项；不能直接宣称都是malloc或memset瓶颈。

因此，优先目标应是**批量准备的串行排序、重复扫描和表示构建**。FS apply不到1秒，其中reverse Commit约0.63秒；继续只优化邻接搬移不可能填平2.18秒缺口。I21默认关闭的裁决仍合理。FS100K比例实验55%～65%的cache占比不能拿来解释10M。

## 3. 本轮实跑的机制实验

目录：`logs/scaling_feasibility_20260916/`。包含源码、独立runner、逐次JSONL、`probe_summary.json`、`stage_sums.json`。编译`g++ -O3 -std=c++17 -fopenmp`；固定NUMA0；radix并行20线程并绑定核心；顺序serial/parallel/parallel/serial。排序包括scratch分配及释放，输入复制、文件读取和结果比较在计时外。两个候选均未接入生产。

### 3.1 稳定并行source radix

取真实更新文件第一批完整10M条记录，保留source/destination/operation顺序，比较与生产相同四轮稳定radix算法的串行版本和按输入连续区间划分、各线程计数/前缀分配/稳定scatter的并行版本。并行输出与串行输出逐字节一致；不是仅比较弱checksum。两次均值，毫秒/一次排序：

| 输入 | 串行 | 并行20线程 | 比值 | 节省 |
|---|---:|---:|---:|---:|
| TW真实10M | 408.369 | 90.923 | 4.49× | 317.446 |
| FS真实10M | 407.843 | 91.308 | 4.47× | 316.535 |
| TW分布重复至100M | 4049.180 | 888.757 | 4.56× | 3160.423 |
| FS分布重复至100M | 4111.285 | 894.326 | 4.60× | 3216.960 |

**100M输入仅是将10M记录重复十次的排序压力fixture，含重复操作，绝不是合法100M动态图实验。** 它只说明1.2GB记录数组下并行稳定排序仍有收益；不覆盖真实100M的新source覆盖率、传播、reverse增长、显存或最终距离。

生产grouping还有输入表示转换与group输出，不能把整个1.7秒grouping乘以4.5倍。OpenMP微实验也不证明生产固定worker池可原样获得同样性能；要控制线程建立、first-touch和NUMA条件。

### 3.3 对胜出机会的含义

若仅为预算评估，将第一批两项净节省乘2：TW约1.227秒，FS约1.660秒。两项属于不同阶段，理论上可组合，但缓存/分配器/worker相互影响尚未测量。

- TW的0.573秒缺口小于该预算，即使只能兑现一部分仍有追平机会；达到比原版快5%的预算1.108秒则需要较充分兑现。这里支持“有较强继续投入理由”，不支持“已经胜出”。
- FS兑现全部两项后，按I20参照仍约11.991秒，高于历史11.468秒。剩余约0.523秒可在reverse排序0.817秒和preflight非reverse部分2.183秒中寻找，但没有证据保证拿到。
- reverse排序若只改善50%，仅约0.409秒，仍不足以单独补上FS剩余差距。不能因同为radix就把12字节source排序的4.5倍直接套到16字节effective排序。
- 已有B5 per-source统计精简负结果继续有效；不以“preflight大”为理由重做同一被否决候选。

## 4. 100M的机会、容量和数据边界

### 4.1 为何仍可能有算法优势

原版PMA `del_edge`逐条更新扫描并搬移该source的邻接；插入路径逐条找空位、可能移动跨source区间并检查rebalance。当前系统按source批量匹配/修改，更多同source更新可摊薄邻接扫描和搬移。I19已经观察到100K→10M每更新写入字节下降：TW246.79→35.74，FS152.75→94.25；不能说每更新放大随batch必然增加。

这提供100M可能受益的机制，却不是胜负证明：原版也可能受局部性、删除释放空位等影响；当前仍付reverse维护、元数据、完整语义和状态发布成本。原版存在重复边删除等语义疑点，不能把少做有效工作视为正常性能优势。

### 4.2 publication显存是具体风险

`framework.cuh::get_update_file`按最大batch更新数调用`ReserveSparsePublicationCapacity`；`TopologyPatchRecord`为24字节：

- 10M：device patch 240MB；100M：2.4GB，增量2.16GB，约2060MiB；另有同大小pinned host patch。
- FS历史10M cache2采样约14710MiB。仅机械叠加该增量已约16770MiB，超过16GB卡16384MiB。这是容量风险估算，**不是实测100M OOM**，其他buffer生命周期与工作集可能变化。
- 发布列表要求严格递增且唯一，容量可先按`min(B,V)`界定：FS约1.575GB、TW约1.262GB，而不必100M都预留2.4GB。进一步可考虑分块发布，在所有块完成后才切换epoch/允许reader，不能边发布边暴露半更新状态。
- affected incoming CSR还可能随删除范围增长，不能只修patch就宣称FS100M能装下。降低cache容量会改变运行配置，需要双方相同资源预算，不能静默换条件。

### 4.3 主存不是本机首要硬容量限制，但布局仍影响时间

本轮读取机器状态：总RAM754GiB、可用约734GiB，磁盘剩余约3.5TB；GPU为16GB V100。100M时原始TopologyMutation约0.8GB，mixed Record及scratch各1.2GB，单phase50M effective与scratch各约0.8GB；这些只是部分表示，生命周期并非全部同时存在。按source的PreparedResult/apply metrics、reverse容器和多批Loader另计，不能据此给出完整峰值。

chunk arena初始化仅预留rounded容量的12.5%额外空间，运行中EnsureAllocationsFit失败会抛arena exhausted，不自动扩容。即使插删数相等，度分布变化、容量按2次幂取整和retire/reclaim时序也可能增加需求。需要实际合法100M的容量replay/画像。

reverse在当前不跨池抵消的scaling更新中，两批10M后overlay为20M；合法两批100M可能达到约200M记录。除存储外，后续phase需要读旧overlay并生成新输出。这条历史成本在10M尚不足以优先立项，在100M需要重新计量；不能按10M结论永远忽略。

### 4.4 100M不是仅把10M时间乘十

当前底图边数：TW196289923，FS903040061。100M混合批次删除50M条，分别约为底图25.47%和5.54%；两批不放回删除相当于约50.95%和11.07%。TW尤其可能发生不同的可达性/SPT失效范围。

原始边池容量足以支持两批100M插删各半，但不能直接拼接/重复10M文件冒充合法流。生成器按`batch * max_each`切片；把最大档改为100M会改变后续batch的小档抽样位置。若需与既有两批10M严格嵌套，需专门保留原批次分配规则或重新生成同cohort参照，不能只改`--scales`后声称历史第二批不变。十批100M在TW10%底图的全程不放回删除契约下需要500M原始底图删除边，超过196M，必须改变批数或重新设计合法更新契约。

## 5. 建议的最小继续投入范围

1. **先做发布source有序合并，再做稳定并行source grouping。** 两者已有真实10M输入机制证据，不更改邻接布局、删除/插入闭包或CPU/GPU职责。用同二进制显式候选开关，完整10M短配对核验净收益；小语义用例覆盖空phase、重复、无效删除和changed-source过滤。
2. **FS仍差时，细分preflight并定向处理reverse排序/有效记录输出。** 保留commit前全部prepare成功的异常契约。不要把所有串行统计删除、恢复I21或重造整套PMA作为第一步。
3. **100M先完成容量设计与合法数据，再各系统各一轮两批筛查。** 记录真实有效更新数、完整P0、阶段时间、内存、affected、overlay与最终结果；采用相同设备资源及明确模式。长实验后台运行，确认健康后不持续轮询。本轮未启动该队列。
4. **止损标准。** TW两项集成若无法稳定填平约0.57秒缺口，或FS组合候选不足以提供约2.18秒净节省，应重新裁决，不继续小粒度扫参；论文若需要有余量的胜出，目标用快5%的1.11/2.76秒预算。100M能跑通只是容量结论，需原版合法同口径结果才能判断速度。

现阶段没有证据要求推翻source-local架构，也没有证据支持“100M必胜”。合理投入是有明确成本预算的批量准备优化；TW10M最有希望先形成完整胜出，FS10M需要多项收益组合，100M应作为新的容量与工作量边界实验。
