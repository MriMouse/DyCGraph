F1-C 的测量条件是对 CPU 单方面有利的：候选 SCC 满足 successor_cut_edges=0, dependent_gpu_service_work=0（完整独立分量），状态用离线稀疏索引，20 核 NUMA-aware 持久 worker。即便如此，两张真实图均无净收益。

2.2 失败的根本原因

I9 实测（10 batch 总量）：

- Twitter exact-source insertion closure：累计 2.7 ms（占 paper time 0.47%）
- Friendster：7.9 ms（0.20%）

CPU 即使把全部 insertion propagation 白拿走，理论最大收益不足 0.5%。Amdahl 分母被自己的 GPU 优化消灭了。deletion repair 则每 batch 仅 3–46 ms（TW）/ 9–150 ms（FS），而跨设备交接固定税无法再降。

2.3 更大数据集能否突破？

uk-2007-05（web 图）：不能。理由如下：

基图规模：105.9M 顶点，~1.99B 边（50p 采样），Sep 3 已生成，尚未运行任何实验。

GPU 内存可行性（两点模型，基于 I10 实测）：

vertex model: peak = 4328 + 153.66 × Mvertex
edge   model: peak = 8391 + 6.66  × Medges

uk-2007 prediction:
  vertex model: 4328 + 153.66 × 105.9 ≈ 20,600 MiB  (V100 上限 16,384)
  edge   model: 8391 + 6.66  × 1992 ≈ 21,669 MiB

当前 Friendster 实测 GPU peak = 14,409 MiB，主机 RSS = 54.2 GB
uk-2007 估算主机 RSS ≈ 125 GB（754GB 可用，不成问题）
uk-2007 估算 pinned memory ≈ 21 GB（Friendster 9.55 GB × 1.99B/903M）

uk-2007 是 web crawl 图（幂律），与 Twitter/Friendster 同类——低直径、小受影响集、insertion closure 极短。即使内存勉强够（需压到 ~25p 基图 + --cache=0），workload regime 与 Twitter 几乎相同，CPU 传播的 Amdahl 分母一样接近零。更大的 web 图不会改变这个结论。

唯一可能有帮助的方向是不同类型的图，见第三节。

10 batch 合计 paper time：2,235,501 ms（约 37 分钟）

3.2 为什么 Europe 这么慢

当前 GPU repair 是 Bellman-Ford 式：每轮扫描全部 affected incoming edges（约 5500 万条），而不是 frontier-based 收缩。实证确认：

- dirty_partitions=512（始终全扫）
- gpu_edge_span_upper_bound 几乎恒定在 ~4 亿（全图边数量级）
- 每轮 throughput 稳定在 2.21–2.56 M edges/ms（spread 16%，近似常数）
- mean wall 约 21 ms/round × 7,697 rounds = ~162 s / batch

对比 Twitter：仅 8–11 轮（SSSP 直径短），每轮扫描 ~2.5 万条 incoming edges。

3.3 CPU 的工作量分析

对于 Europe，理论 CPU Dijkstra 工作量 vs GPU Bellman-Ford：

GPU edge-visits per batch ≈ 56.5M × 7,697 = 4.35×10¹¹
CPU Dijkstra ops          ≈ 56.5M × log₂(26.6M) = 1.38×10⁹
比率 = 313.4x >> 盈亏平衡 77x

CPU 理论优势 = 313.4 / 77 ≈ 4.1x

即使 CPU 比 GPU 慢 77x，对 Europe 做 CPU Dijkstra 在理论上仍然快 4 倍。

这与 Twitter/Friendster 的情况（比率 0.6x，完全不可行）形成了根本性的对比。

3.4 科研意义

这不是简单的"更大数据集"，而是不同的工作负载 regime：

- 社交/web 图（TW/FS/Wiki）：低直径，小受影响集，GPU 几乎每 batch 几轮收敛，CPU 没有优势
- 路网 OSM（Europe）：高直径，受影响集覆盖全图一半，GPU 需要数千轮，算法上是 O(iters × E_affected)，而 CPU Dijkstra 是 O(E_affected × log V)

当前系统对高直径图的 GPU 实现算法上是次优的（全量重扫，非 frontier-based），这是一个独立的研究机会，与前六代 CPU owner 失败的路线完全不同。

具体含义：Europe 在 50p base（50 批 --source=1 当前失败）上如果能正确运行，有可能成为一个展示「高直径路网 SSSP 修复 CPU 优势」的新证据，完全不依赖于社交图上已经死掉的 CPU owner 路线。
