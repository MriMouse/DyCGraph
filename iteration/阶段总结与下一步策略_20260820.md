# C-GpuStreamGraph-CG 阶段总结与下一步策略

日期：2026-08-20  
范围：动态 SSSP 的连续 10 个 100k mixed-update batch。性能采用 batch 内总时间 `paper_algorithm_ms`。

## 1. 迭代过程

### 迭代 A：先确认问题在哪里

- **问题**：删除边后的处理把 CPU 修复、全图数据准备、GPU/CPU 数据传输和大量分区重建混在一起，时间变慢时无法判断原因。
- **做法**：增加删除阶段的正确性检查，并把每个 batch 的时间拆开记录。
- **结果**：Twitter 10 个 batch 中，CPU 真正做最短路计算只用了 `18.524 ms`；主要时间花在全图准备、数据传输和扫描。结论是：单纯把 CPU 最短路算得更快，不能解决主要问题。

### 迭代 B1：确定删除边后的计算位置

- **问题**：删除一条边后，不能只依赖后续插入计算来补救；原来的 CPU 修复也很重。
- **做法**：只找出受删除影响的顶点，并让 GPU 根据这些顶点的入边重新计算最短路。
- **结果**：Wiki、Twitter、Friendster 均通过正确性检查；相对 CPU 修复，完整 batch 时间下降 `30.83% / 34.92% / 32.62%`。删除边后的最短路修复确定放在 GPU 上。

### 迭代 B2：让删除修复只处理必要工作

- **问题**：即使修复逻辑已经转到 GPU，仍有全图状态复制和固定分区重建等无关工作。
- **做法**：只维护受影响顶点队列；只准备这些顶点真正需要的入边；GPU 只扫描这部分数据。
- **结果**：删除了全图状态复制、专用修复副本和固定 512 分区重建。相对 B1，删除阶段时间下降 `68.84% / 88.87% / 71.67%`。这是当前稳定的 GPU 删除修复路径。

### 迭代 B3：首次验证 CPU/GPU 共同算最短路

- **问题**：希望让 CPU 和 GPU 同时处理不同顶点的最短路更新。
- **做法**：给每个顶点指定唯一计算方；CPU/GPU 之间只交换必要的距离更新，并保证双方结束后结果一致。
- **结果**：正确性通过，但 CPU 实际与 GPU 重叠的有效计算时间只有 Wiki/Twitter/Friendster 的 `0.308 / 0.007 / 0.059 ms`。按固定顶点范围分配工作没有端到端收益。

### 迭代 C：CPU 负责准备图更新，GPU 负责计算

- **问题**：一次图更新可能触发原有内存结构的大范围移动，GPU 因而需要收到大量无关的图结构更新。
- **做法**：CPU 只修改本批真正变化的顶点邻接表，并把这些变化整理成小的更新包发给 GPU；GPU 不再接收整张图的结构副本。
- **结果**：建立了“CPU 负责准备图结构变化、GPU 负责最短路计算”的基本分工，也为后续性能优化提供了正确性约束。

### 迭代 D1：减少 GPU 常驻内存

- **问题**：为了追踪图结构版本，GPU 上保留了一份按全部顶点分配的大型辅助表。
- **做法**：去掉这份全量表；只保留 GPU 真正遍历需要的信息，图更新时只传递本批变化的顶点记录。
- **结果**：Orkut/Wiki/Twitter/Friendster 分别减少约 `74 / 312 / 802 / 1506 MiB` GPU 内存，且正确性通过。

### 迭代 D2：减少图更新发布时的等待

- **问题**：GPU 收到图更新后，CPU 立即等待；性能模式还执行了只用于检查的大量核对工作。
- **做法**：提前分配更新缓冲区；正常性能运行只发送一次更新并按流顺序执行，完整核对只保留在 correctness 测试中。
- **结果**：图更新发布时间下降 `93.6%--99.6%`，完整 batch 时间没有回退。

### 迭代 D3：降低 CPU 修改邻接表的代价

- **问题**：CPU 修改邻接表时，删除、复制和扩容仍会产生多余扫描和复制。
- **做法**：先检查整批更新是否可执行，确认后一次提交；按顶点集中处理删除和插入，减少临时容器与重复复制。
- **结果**：相对 C1 的正式 5 次重复中位结果，Wiki 快 `5.7%`，Twitter 快 `37.4%`，Friendster 快 `31.5%`。Orkut 慢 `11.5%`，因此只作为机制样本，不作为总体结论。Twitter 的删除子项仍有回退，未使用数据集特例掩盖。

### 迭代 E：再次验证 CPU 是否适合做图计算

- **问题**：希望寻找比固定顶点范围更合理的 CPU/GPU 图计算分工。
- **做法**：验证按图结构分区、CPU 保留本地状态、只发送真正变化的边界信息，以及 CPU/GPU 异步运行。
- **结果**：CPU/GPU 通信量大幅下降，Twitter/Friendster 分别下降 `96.3% / 98.0%`；但两边的最短路计算仍未获得端到端加速。旧的分区和逐轮等待方案停止。

### 迭代 E4-R1/R2：先把 GPU 基线做紧凑

- **问题**：在讨论 CPU owner 之前，GPU 路径仍有多余的传播和入边准备工作。
- **做法**：GPU 只处理实际发生变化的起点；删除修复时将静态入边和本批变化合并后，仅准备受影响顶点所需数据。
- **结果**：Friendster 10 个 batch 的“准备入边 + 传输 + GPU 修复”平均约 `24.75 ms/batch`，成为后续 CPU owner 的公平基线。

### 迭代 F1-C：最后一次验证删除阶段 CPU owner

- **问题**：验证 CPU 能否接手一个独立的受影响子图，同时让 GPU 处理剩余部分，从而缩短删除修复时间。
- **做法**：记录一次最小状态；CPU 和 GPU 在离线回放中处理互不重叠的顶点；逐点检查最终最短距离。
- **结果**：三组 10 batch 的最短距离均一致。但在两张真实图上，即使使用有利于 CPU 的估算，CPU owner 仍较慢：Twitter `4.514 vs 3.688 ms`，Friendster `44.536 vs 22.770 ms`。R-MAT 上更快，但仅是合成边界样本。结论：停止将 CPU 用作删除阶段的最短路计算方。

## 2. 已形成的主要贡献

- **只修复受影响区域**：删除边后，不再扫描整张图，而是只处理真正受到影响的顶点及其入边。
- **CPU 准备更新，GPU 执行最短路**：CPU 更适合整理图的变化；GPU 更适合大量并行的最短路松弛。
- **图更新只发送变化部分**：GPU 不再接收全图结构副本，只接收本批发生变化的顶点和邻接表记录。
- **降低 GPU 内存和等待**：移除了按全图顶点分配的大型辅助表，减少发布时的 CPU 等待。
- **避免少量更新触发整批缓存重建**：同一批只更新发生变化的缓存内容，不再因少数顶点变化而整体清空、整理和重装缓存。
- **明确了 CPU owner 的适用边界**：固定分区、逐轮跨设备同步、每 batch 临时切分删除子图，在真实动态图上都没有端到端收益。

## 3. 对当前问题的分析

### 3.1 为什么静态 CGgraph-V1.5 能受益，而当前删除阶段不能

- 静态 CGgraph-V1.5 处理的是完整 BFS/SSSP 过程。一轮中可能有数亿条活跃边，CPU 和 GPU 都有足够大的连续任务，可以同时工作很久。
- CGgraph-V1.5 的图结构长期不变。GPU 子图、CPU 数据和状态可跨很多轮重复使用，数据准备成本被摊薄。
- 当前系统处理的是一次动态图更新后的局部修复。Twitter/Friendster 每 batch 中位需要修复的入边约为 `2.2 万 / 22.4 万`，远小于静态系统进入协同模式时约 `2 亿` 活跃边的量级。
- 当前 GPU 已经只修复局部区域。CPU 不是替换一次全图遍历，而是在替换一段已经很短的 GPU 修复工作。
- CPU 并非完全没有算力：Friendster 上 CPU 完成候选局部修复约 `2.9 ms`。问题是每 batch 的状态准备、跨设备交接和结果合并比这部分计算更昂贵。
- R-MAT 的结果说明，当局部修复足够重、GPU 访问条件较差时，CPU 可能有空间；但该条件没有在 Twitter、Friendster 真实图上出现。

### 3.2 CPU topology prepare 路线详细解读

#### 它具体做什么

- 每个 batch 都有边的插入和删除。图结构首先保存在 CPU 内存中，因此 CPU 天然知道哪些顶点的邻接表发生变化。
- CPU 将同一顶点的更新合并：删除哪些邻居、增加哪些邻居、该顶点更新后的邻接表放在何处、邻接表长度是多少。
- CPU 完成这些图结构修改后，只生成“变化顶点清单”。清单中包含顶点编号、新邻接表位置、长度和版本号。
- GPU 收到清单后，只更新这些顶点的访问地址；未变化顶点保持原样。随后 GPU 使用新图结构继续执行最短路计算。
- 这条路线中，CPU **不接手最短路计算**。CPU 的 owner 是“图更新准备”，GPU 的 owner 是“图算法计算”。

#### 它解决了原系统的什么问题

- 原有连续内存图结构为了保持整体布局，修改一个顶点时可能移动很多其他顶点的邻接表。
- 因此 GPU 很难判断哪些数据仍有效，容易退化为大范围重新发布、重新整理缓存、重新加载缓存。
- 新路线把变化限制在真正被修改的顶点：GPU 更新量按“本批变化顶点数”增长，而不是按全图顶点数增长。
- 这也让缓存更新从“整批重建”变成“局部修补”，避免大量无效数据移动。

#### 已有数据说明什么

- D1：删除全图辅助表后，Twitter 和 Friendster 分别减少约 `802 MiB` 和 `1506 MiB` GPU 常驻内存。
- D2：只发布本批变化、取消发布后的同步等待后，发布阶段下降 `93.6%--99.6%`，完整时间没有回退。
- D3：相对 C1 的正式 5 次重复中位结果，完整 10-batch 时间：
  - Wiki：`4216.221 -> 3977.542 ms`，快 `5.7%`。
  - Twitter：`3065.573 -> 1919.521 ms`，快 `37.4%`。
  - Friendster：`7574.769 -> 5184.984 ms`，快 `31.5%`。
- F1-C0：在 Twitter 的一次 10-batch screening 中，避免缓存整批重建后，总时间从 `1618.501 -> 594.654 ms`，快约 `63.3%`。这是单次结果，尚未进行交错重复，不能作为正式性能结论。

#### 这些收益应如何理解

- 不能说上述全部收益都来自 CPU，因为收益来自一组协同变化：CPU 更紧凑地准备图更新、GPU 只接收变化数据、减少缓存重建、减少同步等待。
- 但 CPU 的角色是关键且明确的：它把原先会放大成全图/整批开销的更新，整理成 GPU 可以局部消费的小更新包。
- 这比让 CPU 每 batch 临时获得 GPU 最短路状态、再去计算一小段最短路，更符合两种硬件的数据位置和工作特点。

### 3.3 当前瓶颈

- GPU 删除修复已很紧凑，CPU 可替代的最短路关键路径不足。
- CPU 目前仍要先完成图更新准备，GPU 才能使用新图；两者还没有真正并行。
- Twitter 的删除操作仍可能因邻接表复制或扩容变慢，说明 CPU 更新路径还不够稳定。
- 缓存局部更新已显示很大潜力，但仍缺少缓存空间耗尽时的回退验证，以及 Friendster/Europe 的同等性能数据。

## 4. 下一步策略

### 不再继续的方向

- 不再继续 CPU 参与 deletion SSSP 计算。
- 不再继续固定分区、METIS 划分、固定比例、消息包大小、线程数等参数搜索。
- 不将 R-MAT 的单独成功外推为真实图上的通用结论。

### 新主线：让 CPU 准备下一版本图结构，同时让 GPU 使用当前版本计算

- **目标**：CPU 在准备下一批图更新时，GPU 不必空等，而是继续读取当前稳定图结构完成可以并行的计算。
- **第一步**：只做依赖关系审计，明确哪些工作必须等图更新完成，哪些工作可继续使用当前图结构；不直接扩大 runtime。
- **第二步**：实现一次最小并行原型。CPU 准备下一版邻接表和更新清单，GPU 继续执行当前版本可独立完成的工作；GPU 读完旧版本后再切换。
- **第三步**：完整记录 CPU 准备时间、GPU 计算时间、等待时间、发布新版本时间、内存占用和正确性；所有时间仍计入同一个 batch。
- **验收标准**：Twitter、Friendster、Europe 至少两张真实图的连续 10 batch 总时间稳定下降；最短路结果、图结构哈希和版本顺序全部正确；收益必须能由实际被覆盖的等待时间解释。
- **同时收尾**：验证缓存空间耗尽后的安全回退；补 Friendster/Europe 的局部缓存更新性能与正确性数据；不改变 GPU 作为最短路计算方的结论。

## 5. 汇报结论

- CPU 作为短寿命 deletion SSSP 计算方：真实图数据不支持，停止投入。
- CPU 作为图更新准备方：已有 Wiki `5.7%`、Twitter `37.4%`、Friendster `31.5%` 的正式端到端正收益，值得继续。
- 下一步不是让 CPU 多算一点最短路，而是让 CPU 准备下一版图结构的工作与 GPU 使用当前图结构的计算重叠，进一步缩短动态更新的关键路径。
