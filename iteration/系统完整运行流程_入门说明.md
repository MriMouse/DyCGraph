# C-GpuStreamGraph-CG：从输入到一批更新完成的完整运行流程

本文按当前代码和当前研发结论，说明一次 `hybrid_sssp` 运行到底做了什么。读者只需要会基本编程；文中第一次出现的术语都会解释。示例使用很小的图，真实图可能有数千万顶点和数十亿条边。

## 先记住三类数据

一条边写成 `u -> v`，表示从顶点 `u` 可以走到 `v`。每条边还有一个权重；当前 SSSP 示例代码用 `(u+v)%128` 生成 0--127 的权重。

系统长期保存三类状态：

1. **当前图**：每个顶点的出边列表。它是 CPU 侧的权威拓扑。
2. **反向查找表**：给定 `v`，快速得到所有 `u -> v` 的边。删除边后必须用它寻找替代路径。
3. **GPU 计算状态**：每个顶点的距离、父节点、是否受影响等数组，以及 GPU 上的边数据和临时队列。

例如图中有 `0->1, 0->2, 1->2`，从 0 出发时距离可能是 `d[0]=0,d[1]=w(0,1),d[2]=min(w(0,2),w(0,1)+w(1,2))`。

## 程序如何启动

大直径/长传播模式通过`CG_ORDERED_REPAIR=1`开启，默认同时使用**有序删除修复和有序插入传播**（I22整合）。普通模式默认使用block插入传播。大直径模式优先于`CG_INSERTION_SCHEDULE`：即使环境遗留block/thread也仍使用ordered，无需unset。仅关闭大直径模式时，`CG_INSERTION_SCHEDULE=block|thread|ordered`才控制插入策略。`CG_BATCH_MAINTENANCE=regular|large|auto`独立控制CPU拓扑维护，不决定传播模式。日志`[I22-SCHEDULE]`显示实际策略、选择来源和大直径模式状态。

命令通常类似：

```bash
./build/hybrid_sssp \
  -graphfile input.txt -updatefile update.txt -update_size stream_size.txt \
  -format market_big -source_node 0 -cache 2 -hybrid 0
```

`main.cu` 创建通用运行骨架 `Skeleton<hybrid_sssp::App>`，骨架负责解析参数、加载图、调用 `HybridSSSP()`，结束时调用 `cudaDeviceReset()`。SSSP 的具体工作在 `samples/hybrid_sssp/hybrid_sssp_host.cu/.cu` 和 `include/framework/` 中。

输入图每行是 `source destination`；更新文件每行是 `a source destination` 或 `d source destination`；`stream_size.txt` 每行给出本批新增数和删除数，例如 `2 3` 表示本批读 2 条新增边、3 条删除边。

## 阶段一：CPU 读取和建立初始图

CPU 顺序读取输入边，把相同 source 的出边整理到连续数组中。常见形式是 CSR：

```text
offset[0]=0, offset[1]=2, offset[2]=3 ...
edges=[1,2,2,...]
```

顶点 `u` 的出边位于 `edges[offset[u] ... offset[u+1])`。这样 GPU 线程读取一个顶点的邻居时可以连续访问内存。

同时 CPU 建立反向查找结构。当前 `DynamicReverseIndex` 以“目标顶点 -> 来源顶点列表/计数”的方式保存入边；它不是 C++ 的 `std::map` 必然实现，而是一个封装好的动态索引，支持重复边计数和删除一个边实例。

## 阶段二：把初始图和计算数组送到 GPU

CPU 申请并填充距离数组、父节点数组、标记数组；源点距离设为 0，其余为无穷大。CUDA 把 CSR 边数组和这些状态复制到 GPU 全局显存。GPU 后续用成千上万个线程并行处理不同顶点或不同边；一个线程通常负责一个顶点/边位置，具体块大小由 CUDA kernel 配置决定，不是固定的“一个线程对应一条完整路径”。

初始 SSSP 会执行若干轮松弛：线程读取边 `u->v`，计算 `distance[u]+weight`，若更小则更新 `distance[v]`。更新通过原子操作或双缓冲避免并发写坏数据。同步模式在轮次之间等待，异步模式允许更新立即传播；当前增量主路径默认使用 GPU pull 语义。

## 阶段三：CPU 读取一批更新并过滤

CPU 按 `stream_size.txt` 切出本批记录，分成删除和新增。`EffectiveUpdateBatch` 会去除无效记录、保留重复边语义，并按 source/destination 形成可处理的分组。

例：当前只有 `0->1`，批次包含删除 `0->1` 和删除 `0->9`，后者没有对应边，会被记为 missing delete，不会悄悄改变图。

## 阶段四：先执行删除（CPU 修改拓扑）

删除阶段必须先于新增阶段，因为删除后的图是 repair 的输入。

`SourceLocalChunkStore` 按 source 分组。每个 source 有自己的 chunk（可理解为可增长的小型连续边数组），而不是每条更新都单独 `malloc`。CPU worker 线程并行处理互不相同的 source：

1. 计算删除后该 source 的新度数；
2. 在预检查阶段确认空间足够；
3. 生成新的 chunk 内容，跳过被删的边；
4. 串行提交 epoch、边数、回收旧 chunk，并发布新版本。

并行只发生在 source 的准备和重写；分配预检查、版本提交、旧内存回收和最终发布保持批次级串行，避免读线程看到半完成拓扑。

例：`0` 有 `[1,2,3]`，删除 `0->2`，worker 为 source 0 生成 `[1,3]`；另一个 worker 可同时重写 source 5，但两者不会写同一份 chunk。

## 阶段五：建立本批 reverse 更新

删除和新增记录都需要按 destination 分组，因为后续要知道每个目标顶点有哪些入边变化。

默认路径可以把所有记录放进一个共享结构；大批量实验候选 `CG_REVERSE_SHARDS=64` 则先按 destination 范围拆成 64 个 shard。每个 shard 内部完成排序/分组、统计目标所需槽位、分配连续空间、写入边记录，最后再由 CPU 串行提交统一版本。

例：更新 `1->9, 4->9, 3->20`，目标 9 的两条记录进入同一 shard 和同一目标组，目标 20 进入另一组。分片减少单个全局表扩容和线程竞争；它改变的是更新组织和调度，不改变图的含义。

## 阶段六：GPU 删除修复（决定哪些距离失效）

删除一条边可能使多个顶点原来的最短路径失效。CPU 根据旧父节点关系先产生受影响顶点集合；GPU 对这些顶点检查当前有效入边：

```text
对 v 的每条入边 u->v：候选 = distance[u] + weight(u,v)
取最小候选；没有候选则 v 变成不可达
```

传统 pull 每一轮都让受影响顶点扫描入边；长路径可能需要几千轮，于是同一批入边被反复读取。EU/USA 就出现了数百亿次逻辑检查。

当前默认 GPU pull 会维护 affected/frontier 数组并反复迭代，直到没有顶点变化。每轮 GPU 线程并行检查不同顶点的入边；轮末读取计数并决定是否继续。

实验性的 ordered GPU 使用距离桶：`Delta=128` 时，距离 0--127 放桶 0，128--255 放桶 1，以此类推。每次取最小的非空桶；桶内顶点仍由大量 GPU 线程并行松弛，新产生的顶点进入后续桶。稀疏 active-list 只保存当前真的活跃的顶点，避免每轮扫描整个 affected 数组。该模式主要适合长传播 SSSP，不是所有图算法的通用规则。

## 阶段七：发布删除后的 GPU 状态

GPU 把新的距离、父节点和受影响标记写回设备状态；必要的统计信息复制回 CPU。CPU 确认 kernel 完成后，发布删除后的拓扑版本，使后续新增阶段看到一致状态。生产路径要求距离、父节点、边计数和 epoch 一致；测试模式还会检查 Bellman 条件和 tight witness（即每个有限距离顶点至少有一条边能解释该距离）。

## 阶段八：执行新增并传播改进距离

CPU 把本批新增边写入 source-local chunk，并更新 reverse index。新增边可能提供更短路径，GPU 将新增边的源点作为种子。

默认 GPU 路径重复进行 frontier 松弛：活跃顶点读取出边或目标顶点读取入边，发现更小距离就写入并加入下一轮队列。插入传播可能越出删除阶段的 affected 集合，因此不能复用过小的删除队列容量。

ordered GPU 在这里也可以使用桶，但当前实验显示 EU/USA 1000k 的主要剩余成本已经转到插入传播（约占 ordered 总时间 77%/82%），所以后续要研究 insertion wave 合并、frontier 去重和 processed-edge 减少。

## 阶段九：缓存刷新（如果启用 `-cache`）

cache 是图边的一部分驻留在 GPU 的容量预算。CPU 根据候选顶点和拓扑变化决定哪些边应保留，GPU/CPU 执行装载、驱逐和 compact。compact 会复用已有设备队列前缀，减少临时显存；所有分配、复制和释放都计入完整 batch 时间。

当 cache、patch staging、repair workspace 和 epoch 数组同时存在时，峰值可能超过显存。FS 10000k 的 OOM 就发生在这个共存阶段；失败触发点是一个约 250 MiB 的数组申请，但根因是多个生命周期重叠，而不是单个数组本身。

## 阶段十：最终检查和进入下一批

CPU/GPU 完成同步后记录本批计时、更新数量、扫描量、传播轮数、峰值显存和 checksum。`check=true` 时还运行 Bellman 和 tight-witness 检查；`check=false` 只用于性能测量。通过后保留新拓扑、距离、父节点、cache 和 reverse index，读取下一行 `stream_size.txt`，重复阶段三到十。

## push/pull 与 sync/async 在哪里

仓库早期框架仍保留 `SYNC_PULL_TD`、`ASYNC_PUSH_DD` 等组合。push 是变化源点沿出边通知邻居，pull 是目标顶点扫描入边；sync 是轮次结束后统一生效，async 是更新可立即传播。它们是通用框架能力。当前增量 SSSP 默认 repair 使用 pull；ordered GPU 额外引入距离顺序和稀疏队列，不能简单等同于“换成 push”。未来可以研究 ordered+push，但删除失效判断、并发写冲突和 parent 语义仍需单独证明。

## 当前可选模式的准确说法

系统不是三个自动切换的完整程序，而是两个阶段的人工候选：

- 默认：GPU pull，reverse 单分片；
- 长传播 SSSP：人工尝试 ordered GPU；
- 大批量 reverse 准备：人工尝试 destination 分片（例如 64）；

两种候选可以组合，例如“64 分片 + ordered GPU”，但没有经过验证的自动阈值。小批量分片可能变慢，短传播图通常不值得 ordered。I18 才会把通过成本、空间和状态交接 gate 的候选正式接入生产参数。
