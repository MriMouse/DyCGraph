# 当前动态 GPU 图系统：创新点与完整流程通俗解读

> 面向读者：具备一般计算机编程知识，但没有图计算、GPU 图系统或本项目代码背景。
>
> 用途：理解论文系统并准备口头汇报。
>
> 解读依据：`paper/overview/overview.md`、`iteration/当前系统创新主线凝练与真实性核对_20260917.md` 与 `paper/第三至第五章架构与写作方案_20260917.md`。

## 1. 先用一句话说明这个系统

这是一个处理**不断发生边更新的大图**的系统：完整图太大，不能全部放进 GPU，因此 CPU 保存完整图结构，GPU 保存计算结果并负责主要计算；每来一批边的删除和插入，系统只维护真正改变的局部图结构，也只重新计算真正受影响的局部结果。

当前论文用 **SSSP（单源最短路径）** 说明系统。SSSP 的问题是：给定一个起点，求它到图中每个顶点的最短距离。例如，以北京为起点，图中的顶点是城市，边是道路，边权是路程，SSSP 要计算北京到所有城市的最短路程。

这个系统的重点不是“第一次在 GPU 上算最短路”，而是解决下面这个更具体的问题：

> 当一张放不进 GPU 的大图持续变化时，怎样避免每批更新都大范围搬动图数据、传输整张图的索引，并从头扫描大量无关顶点和边？

系统抓住了两种**区域性（regionality）**：

1. **拓扑区域性**：一批更新通常只修改部分顶点的出边。
2. **结果区域性**：少数边发生变化后，最短距离可能只在部分顶点中变化。

这两个区域有关，但并不相同。某条边虽然只在一个位置被删除，它造成的最短路失效却可能沿着原最短路径向下传播很多跳；恢复某个失效顶点时，还可能需要读取影响区域以外、但本身没有变化的邻居。

因此，系统分别处理“哪些图结构真的变了”和“哪些计算结果真的受影响”，然后用清晰的数据契约把两部分连接起来。

这里特意使用“区域性”，而不是计算机体系结构中常见的“访问局部性”。区域不要求在顶点编号上连续，也不要求在内存中相邻，还可能由多个不连通的小集合组成。它只表示实际变化或依赖影响往往局限在全图的一部分。

区域性是一种可利用的工作负载特征，不是“小批次一定只影响少量顶点”的定理。删除一条关键边也可能影响大半张图；affected 顶点很少时，它们的入边也可能很多。因此，论文不能据此宣称每批复杂度必然只与更新条数或 affected 顶点数成正比。

## 2. 理解系统前需要知道的基础概念

### 2.1 图、顶点、边和边权

图由顶点和边组成。本文处理的是有向加权图，一条边可以写成：

```text
u --权重 w--> v
```

- `u` 是边的起点，也叫 **source**。
- `v` 是边的终点，也叫 **destination**。
- `w` 是边权。在道路图中可以理解为路程或耗时。

系统假设顶点集合固定，变化的是边：边可以被插入或删除。

### 2.2 流式图和批次更新

“流式”表示图持续变化。系统不会每收到一条边就完整执行一次，而是把一段时间内的更新组成一个 **batch（批次）**。一个批次中可以同时包含：

- 删除边，例如删除 `a -> b`；
- 插入边，例如新增 `c -> d`。

批处理可以摊薄调度和传输开销，也更适合 GPU 并行执行。

### 2.3 松弛操作

最短路算法最核心的操作叫 **relaxation（松弛）**。假设已知：

```text
dist[u] = 10
边 u -> v 的权重 = 3
dist[v] = 20
```

经过 `u` 到 `v` 可以得到长度 `10 + 3 = 13`，比当前的 `20` 更短，所以把 `dist[v]` 更新为 `13`。如果 `v` 真的被改善，就继续检查 `v` 的出边，看它能否改善更多顶点。

### 2.4 parent、依赖和失效传播

系统除了保存每个顶点的最短距离，还会保存一个 **parent（父节点）**，表示当前最短路径最后是从哪个顶点走来的。

例如：

```text
source -> ... -> u -> v
```

如果 `v` 的最短距离来自 `u -> v`，那么 `parent[v] = u`。删除 `u -> v` 后，`v` 当前的答案可能失效；依赖 `v` 的后继也可能失效，于是形成一条失效传播链。

### 2.5 outgoing、incoming 和反向索引

- **outgoing adjacency（出邻接）**：从某个顶点出发的所有边。
- **incoming edges（入边）**：所有指向某个顶点的边。
- **reverse index（反向索引）**：按终点查询入边的数据结构。

最短路向外传播改善时，需要看一个顶点的出边；某个顶点的原路径失效、需要寻找替代路径时，需要看它的入边。因此正向邻接和反向索引承担不同角色。

### 2.6 worklist、frontier 和 queue

三者在本文语境中都可以理解为“当前待处理的顶点集合”。如果一个顶点的结果刚刚变化，它会被放入队列；GPU 取出它，扫描它的边，产生下一批待处理顶点，直到队列为空，即达到收敛。

### 2.7 descriptor

CPU 保存完整邻接，但 GPU 必须知道每个顶点的邻接在哪里、有多少条边。本文把这类元数据称为 **descriptor（描述符）**，可以粗略理解成：

```c
struct Descriptor {
    Edge* address;  // 该 source 的邻接起始地址
    int degree;     // 出边数量
    // 还可能有容量等信息
};
```

descriptor 不是邻接边本身，而是 GPU 查找邻接的“目录项”。文档中一个变更 source 的 descriptor patch 大小是 24 字节。

### 2.8 resident、hot cache 和 Zero-Copy

- **resident**：某个顶点的邻接已经驻留在 GPU 缓存中。
- **hot vertex / hot subgraph**：近期经常访问的顶点或子图，适合留在 GPU 中。
- **Zero-Copy**：邻接没有复制进 GPU 显存时，GPU 可以通过 PCIe 直接读取映射的 CPU 主存。

可以把它理解为两级访问：热点邻接放在 GPU，访问快；其他邻接仍在 CPU 主存，GPU 需要时跨 PCIe 读取。

必须明确：GPU 热子图、热度选择、缓存 chunk、Zero-Copy 都是原系统 Grapin 已有的基础，不是当前工作的原创点。

### 2.9 fixed point 和 closure

- **fixed point（不动点）**：继续执行也不会产生新变化的状态。
- **closure（闭包传播）**：从一组初始事件出发，不断传播其影响，直到队列为空。

在本系统中，“恢复到收敛”“传播到队列为空”都表示算到不动点，而不是只做一轮。

### 2.10 三个不能混为一谈的集合

| 集合 | 由什么决定 | 用来做什么 |
|---|---|---|
| **changed sources** | 哪些边起点的邻接实际发生变化 | CPU 拓扑维护与 GPU descriptor 发布 |
| **affected vertices** | 哪些顶点的旧结果因删除依赖而失效 | 删除后的距离恢复 |
| **active sources** | 当前传播波中哪些顶点刚获得有效改善 | 展开出边并推进插入传播 |

三者可能重合，但没有包含关系。一个 changed source 可能导致多跳以外的顶点 affected；一个 affected 顶点恢复后又可能成为传播中的 active source；也有 changed source 的边更新根本不改变任何距离。

还要区分**最终结果变化集合**：它是批前和批末结果真正不同的顶点集合，只能在结果出来后判断。它不能直接替代执行中的 affected queue 或 active queue。例如一条边先删除又插回，批末距离可能不变，但删除中间阶段仍然必须正确恢复。

### 2.11 一批更新中的三个图状态

为了讲清删除与插入的先后关系，可以使用下面三个符号：

```text
G_t      ：本批开始前的旧图
G_t^-    ：应用本批有效删除、尚未应用插入的中间图
G_{t+1}  ：再应用本批插入后的最终图
```

系统先在旧图 `G_t` 上识别依赖失效，再在删除后图 `G_t^-` 上恢复到 fixed point，最后在最终图 `G_{t+1}` 上传播插入改善。`G_t^-` 只是内部正确性阶段，不作为对外查询快照，也不能把当前实现描述成直接在最终图上做一次统一事务闭包。

## 3. 原系统 Grapin 已经做了什么

理解论文贡献时，最容易犯的错误是把继承来的系统能力也说成当前工作的创新。当前系统建立在 Grapin 上，以下能力已经存在：

1. **GPU 增量图计算**：边删除后沿依赖关系让旧结果失效，再迭代恢复；边插入后继续传播更短的距离。
2. **GPU 上的并行调度**：使用 warp 或 block 协作处理顶点和邻接。warp 是 GPU 中一组同步执行的线程，block 是更大的线程协作单元。
3. **GPU 热子图缓存**：根据访问热度选择部分邻接驻留 GPU，并跨批次保留仍然有用的数据。
4. **缓存空间管理**：包括缓存块分配、驱逐、压缩回收和装载。
5. **CPU 保存动态拓扑**：完整图由 CPU 维护，GPU 保存定位邻接所需的索引。
6. **PCIe Zero-Copy**：GPU 可以直接读取映射的主存邻接，并对访问进行合并和对齐优化。

所以汇报时不要说：

- “我们提出了 GPU 增量最短路”；
- “我们提出了 GPU 热子图缓存”；
- “我们首次让 GPU 直接读取 CPU 内存”；
- “我们首次用一个 warp 处理一个顶点”；
- “我们首次让同一 source 的邻接连续存放”。

当前工作的真正贡献，是在这些已有能力上，把更新维护和增量计算进一步缩小到必要范围，并控制长传播中的重复工作。

## 4. 原系统留下的核心低效

这些低效可以归纳为两种“放大”：

- **维护放大**：拓扑本来只改了一小部分，却引起更大范围的存储搬移、重复更新解释、descriptor 发布或缓存维护。
- **计算放大**：算法结果本来只影响一部分，却引起全点启动、整分区扫描、重复准备或同一邻接反复扩展。

“放大”在这里是分析视角，不是一个已经统一测量的倍率。论文要分别通过搬移量、发布字节、准备数据量、处理边数和完整批次时间验证具体机制。

### 4.1 图只改了一小块，存储变化却可能扩散

原系统 CPU 端使用 PMA 一类的紧凑布局保存邻接。它适合连续扫描，但当某个 source 的邻接增长、空间不足时，可能需要做 rebalance，即搬动附近的数据来重新分配空间。

问题是：明明只给顶点 `s` 加了一条边，扩容却可能移动别的 source 的邻接。它们的 GPU descriptor 也随之变化。这样就不能简单地说“只向 GPU 发布请求中出现的 source”，因为未直接更新的 source 也可能被搬动。

原执行链最终会重新复制约 `V+1` 个 descriptor，其中 `V` 是顶点总数。大图中，即使一批只改了少数 source，也可能付出与全图顶点数相关的发布成本。

### 4.2 插入阶段从所有顶点启动，扫描大量无关工作

本地原版在更新后会重建全顶点 worklist，再通过分区调度执行。这虽然能保证不漏掉可松弛的边，但会把大量完全未受影响的顶点也放进启动范围，并可能扫描整个分区中的无关边。

### 4.3 不能在删除尚未恢复时只靠新增边启动

一个看似自然的优化是：插入了哪些边，就只松弛这些新增边，然后向外传播。但混合批次里还有删除操作，这样做可能出错。

例如：

```text
原最短路径：source -> ... -> u -> v
仍存在的替代边：x -> v
本批删除：u -> v
本批新增边：发生在图中另一个区域
```

删除 `u -> v` 后，`v` 原距离失效。它可能通过没有变化的 `x -> v` 恢复。但是 `x` 没有被新增边激活，因此只从新增边启动不会主动检查 `x -> v`，就可能留下错误结果。

因此，精确插入启动必须建立在一个正确性前提上：**先把删除造成的影响完全恢复到不动点**。这样，插入开始前，所有旧边都已经没有遗漏的改善机会，后续只需用新增边作为新的变化来源。

### 4.4 热点邻接只改了一点，仍可能走完整缓存维护流程

原系统已经可以保留未变化的缓存内容，但 touched source 的缓存会失效，批次随后可能执行驱逐、压缩和重新装载。若一个热点顶点仍应留在缓存中，而且新邻接能放回原空间，那么完整维护链会显得过重。

### 4.5 只处理受影响顶点，仍可能重复扫描很多边

精确 frontier 能排除无关顶点，却不能保证同一顶点只处理一次。

假设某个顶点先得到距离 `100`，系统立即从它向外传播；稍后它又得到更好的距离 `50`，它的出边就要再扫描一次。长距离传播中，这种“先传播较差值、后传播较好值”的情况可能大量发生。

## 5. 当前系统的一批更新如何完整运行

下面按时间顺序解释一批混合更新。整个流程可以概括为：

```text
接收更新
   ↓
按 source 分组，建立删除视图和插入视图
   ↓
在旧图上识别删除造成的失效顶点
   ↓
真正删除边，维护正向邻接和反向索引
   ↓
只为失效顶点准备入边，并在 GPU 上恢复到收敛
   ↓
真正插入边，维护正向邻接和反向索引
   ↓
只发布发生变化的 source，并修补可复用的 GPU 缓存
   ↓
只松弛新增边，把真正改善的顶点放入 GPU 队列
   ↓
GPU 在设备内传播到队列为空
```

### 第 1 步：一次分组，生成两个阶段的更新视图

CPU 收到混合批次后，按 source 做一次稳定分组，同时保留删除视图和插入视图。

“稳定”表示同一 source 内仍保留必要的原始顺序。一次分组的结果可以被正向邻接、反向索引和 GPU 发布共同使用，避免各模块分别解释同一批请求。

这一阶段还要区分：

- **请求删除**：输入中要求删除某条边；
- **有效删除**：图中确实存在并被成功删除的 occurrence；
- **请求插入**与**实际插入**。

如果图中 `s -> a` 只有两份，批次却请求删除三次，那么有效删除数只能是两次。后续反向索引也必须收到 `-2`，不能收到 `-3`，否则正向图与反向索引会不一致。

### 第 2 步：在旧图上识别删除造成的 affected 集合

删除真正生效前，GPU 根据旧图中的 parent 依赖，从被删除的依赖边出发传播失效，并直接形成紧凑的 **affected queue**。

`affected` 指“当前最短距离因删除而需要重新确认或恢复的顶点”。紧凑队列只保存这些顶点，而不是建立一个长度为全图顶点数的稀疏标记后再全图扫描。

为什么要在旧图上识别？因为旧图中保存着“谁依赖被删边”的关系。先识别依赖，再删除物理边，逻辑更清楚，也不会丢掉失效传播所需的信息。

### 第 3 步：应用有效删除并更新 reverse index

CPU 根据删除计划修改每个相关 source 的出邻接，并用同一份 `EffectiveEdgeDelta` 更新反向索引。

这里采用准备与提交协议：先排序、归约并确认 reverse index 有足够空间，成功后再让 forward 修改可见，最后提交反向变化。目的不是实现数据库级通用事务，而是避免正向邻接已经修改、反向索引却因准备失败而停留在旧状态。

### 第 4 步：只为 affected 顶点准备 incoming

恢复一个失效顶点 `v` 时，需要找所有仍存在的 `x -> v`，检查能否通过某个 `x` 得到替代距离。因此 CPU 通过 reverse index，只物化 affected 顶点的入边，形成紧凑的 offsets/source 数组，再传给 GPU。

这里的关键是“双重局部化”：

- 顶点范围只限于 affected；
- 传输的边只限于这些顶点的 incoming dependencies。

传输量并不是严格等于 affected 顶点数，而是取决于这些顶点总共有多少条入边。一个 affected 顶点若入度很大，仍可能传输很多数据。

### 第 5 步：GPU 完成删除后的独立恢复

GPU 查看 affected 顶点的入边，使用未失效区域中仍然正确的距离作为边界值，计算替代距离，并在 affected 区域中反复传播，直到不再有变化。

可以把这理解为：图的一块区域因为删除而“断电”，系统不重算整张图，而是从区域边界上仍然可靠的值出发，把内部答案重新求出来。

完成这一步后，系统满足一个很重要的状态约束：

> 对删除后的图，所有旧边都已经处理完毕，没有任何尚未传播的距离改善。

这正是下一阶段只从新增边启动仍然正确的原因。

### 第 6 步：应用插入，并合并 changed sources

CPU 再应用插入边，更新正向邻接和 reverse index。删除阶段与插入阶段中真正发生邻接变化的 source 被合并成最终 `changed sources` 集合。

注意，这不是把删除和插入合成一次最终态计算。删除恢复和插入传播仍是两个有先后关系的阶段；共享的是分组计划、有效变更记录和最终发布集合等准备数据。

### 第 7 步：只向 GPU 发布 changed-source descriptor

每个 source 的邻接独立分配后，一个 source 扩容不会搬动其他 source。于是系统可以只发送 changed sources 的 descriptor patch，并在 GPU 上 scatter 到对应位置。

这里有一个必须遵守的时序：descriptor 发布完成后，依赖它的 GPU kernel 才能读取；旧邻接块也必须等先前读者完成后才能回收。实现用 stream event 和 epoch/retire 管理保证这种可见性与生命周期。

### 第 8 步：同时修补仍驻留的 GPU 邻接

如果 changed source 的邻接已驻留 GPU，发布阶段尝试就地修补：

- 新邻接长度不超过原有效空间时，复用原槽位；
- 邻接增长时，尝试使用该缓存分配尾部的空闲空间；
- 放不下时，使该缓存项失效，后续回到普通冷数据访问和常规刷新流程。

修补时复制的是该 source 的**当前完整邻接**，不是仅复制几条增删差量。因此这里的局部性是 source 粒度。

系统仍会运行原有的热度计算和候选选择。只有当目标 resident 集合中的每个顶点都有有效内容，而且目标数量与已发布集合一致时，才跳过 eviction、compact、load 这一整条常规维护链。

### 第 9 步：只松弛本批新增边

删除恢复已经完成，所以此刻所有旧边都处于稳定状态。系统只检查本批新增边：如果某条新增边真的改善了 destination，就把该 destination 放入 GPU work queue；没有改善就不产生后续工作。

这叫**成功事件驱动**：一条更新存在，不代表它一定影响答案；只有原子松弛确实成功，才调度后续传播。

### 第 10 步：GPU 在设备内传播到收敛

队列中的每个顶点作为 active source，展开自己的出邻接。若它成功改善其他顶点，这些顶点进入下一波队列。GPU 使用双队列不断交换当前波和下一波，直到队列为空。

`(epoch, wave)` ticket 用于去重：同一顶点在同一波即使被多个线程同时改善，也只进入一次队列；若它在后续波又获得更好的距离，仍允许再次激活。

这段闭包在 GPU 设备内判断是否结束，不需要 CPU 在每一波之间接管和重建 worklist，从而减少 host-device 同步。

## 6. 两项总体设计及其内部机制

正式论文对外适合讲**两项总体方法贡献**，与第四章和第五章一一对应：

1. **更新友好的异构图组织**：利用拓扑区域性，减少维护放大。
2. **影响驱动的增量图计算**：利用结果区域性，减少计算放大。

下面的源隔离、统一变更、影响域恢复、有序传播等是两项设计内部相互衔接的机制，不应全部拆成同一级别的“若干独立创新”。这种组织比按研发阶段罗列四条主线更适合论文汇报，也更符合第三至第五章的正式写作方案。

## 6.1 总体设计一：更新友好的异构图组织

这一设计对应论文第四章，由三个递进机制构成：

```text
源隔离图布局
    → 给局部修改建立稳定的物理边界
统一变更视图
    → 给 forward、reverse 和 publication 提供一致语义
增量视图维护
    → 把实际变化安全发布给 GPU 消费者
```

### 它解决什么问题

原紧凑存储中，一个 source 扩容可能搬动其他 source，导致 descriptor 变化范围超过请求范围。因此，单纯记录 touched sources 并做稀疏 memcpy 不足以保证正确。

### 它怎么做

1. 每个 source 使用独立连续邻接块；一个 source 扩容只替换自己的块。
2. 批次按 source 规划，先做容量检查，再并行 compact、append 或 rewrite。
3. forward 邻接产生实际生效的 `EffectiveEdgeDelta`，reverse index 和 GPU 发布都消费同一事实。
4. 只有真正发生邻接变化的 source 进入发布集合。
5. GPU 只接收这些 source 的 descriptor patch。

用第四章的正式术语来说：

- **源隔离图布局（Source-Isolated Graph Layout）**解决“改一个 source 为什么不会带动其他 source 地址变化”。
- **统一变更视图（Unified Change View）**解决“多个拓扑视图如何对一次更新保持同一理解”。“统一”指语义一致，不要求所有模块只共享一个物理数组。
- **增量视图维护（Incremental View Maintenance）**解决“CPU 拓扑变化后，GPU 如何只接收局部 descriptor 仍看到完整正确的最终图”。这里的 view 指 GPU 使用的拓扑表示，不是在声称发明数据库领域的一般增量视图维护。

### 为什么不只是“换了一个数据结构”

真正的贡献是一个端到端契约：

```text
source 更新相互隔离
        +
实际生效的更新只有一份权威表示
        +
forward / reverse / GPU publication 共享它
        +
最终可以安全地做 changed-source 稀疏发布
```

如果没有第一步，未触及 source 也可能移动；没有有效变更记录，正向和反向结构可能对重复删除产生不同理解；没有发布时序，GPU 可能读到旧 descriptor 或已回收的内存。

### 一个具体例子

顶点 `s` 原有邻接：

```text
[a, a, b]
```

批次请求：删除 `a` 三次，新增 `c` 一次。

实际过程：

```text
有效删除只有两次：EffectiveEdgeDelta(s, a, -2)
删除后邻接：[b]
完成删除恢复
实际插入一次：EffectiveEdgeDelta(s, c, +1)
最终邻接：[b, c]
只发布 s 的新 address / degree
```

其他 source 的邻接地址不会因为 `s` 扩容而变化。

### 可以怎样准确表述创新

可以说：

> 我们将 CPU 权威拓扑改为 source-local 的更新隔离布局，并以统一的有效变更记录贯通正向邻接、反向索引和 GPU descriptor 发布，使发布范围能够安全地缩小到真正变化的 source。

不要说“首次在 CPU 维护图”“首次连续保存邻接”“提出 Zero-Copy”。

## 6.2 总体设计二：影响驱动的增量图计算

这一设计对应论文第五章。它分成三个层次：影响决定恢复范围，成功改善决定传播事件，负载特征决定额外的执行特化。

### 它解决什么问题

若插入阶段从所有顶点启动，会扫描大量无关数据；若简单地只从新增边启动，又会漏掉删除后需要通过旧边恢复的路径。

### 它怎么做

1. 删除前，GPU 直接输出 compact affected queue。
2. 删除后，CPU 只准备 affected 顶点的 incoming。
3. GPU 在 affected 区域完成删除恢复，直到收敛。
4. 在这个正确性前提下，插入阶段只松弛新增边。
5. 只有成功改善的 destination 入队，GPU 只展开这些 active sources 的出邻接。
6. GPU 自己交换队列和检测结束，不在每一波回到 CPU。

### 它真正创新在哪里

这项贡献不是一般意义上的“增量图算法”，也不是第一次使用 frontier，而是把下面三件事闭合成一条正确的生产路径：

```text
删除影响精确识别
    → affected-only 依赖准备和独立恢复
    → 删除图先达到不动点
    → 新增边成为插入阶段唯一必要种子
    → 成功事件驱动 GPU source closure
```

独立删除恢复是精确插入启动的正确性条件，二者不能拆开包装成互不相关的优化。

### 可以怎样准确表述创新

> 我们把删除造成的失效直接压缩成 affected 队列，只为这些顶点准备入边并独立恢复到不动点；因此插入阶段可以仅以新增边的成功松弛作为种子，在 GPU 内执行精确的活动 source 闭包，避免全顶点启动和分区范围扫描。

从第五章术语看，前半部分叫**影响域恢复（Affected-Region Recovery）**，后半部分叫**改善驱动传播（Improvement-Driven Propagation）**。两者构成正确性闭环：没有删后 fixed point，新增边不是完备的启动集合；没有成功事件闭包，新增边造成的多跳改善又不能传播完整。

## 6.3 设计一的实现补充：修补 resident 邻接并有条件跳过缓存维护

### 它解决什么问题

某个热点顶点虽然邻接发生变化，但它仍然属于下一批要保留的热点集合。如果缓存空间足够，先让它失效，再执行驱逐、压缩和重新装载，会产生多余工作。

### 它怎么做

descriptor 发布时，同时尝试修补 changed resident source 的完整邻接；随后检查新的目标 resident 集合是否已经全部有效。只有条件完全满足，才跳过常规缓存维护链。

### 为什么只算配套机制

热度统计、候选排序、GPU hot cache、缓存 chunk 管理和跨批保留都是 Grapin 已有能力。当前新增的只是：

- 把 source 级邻接修补并入局部发布；
- 增加一个严格的 refresh gate，判断能否跳过维护链。

因此，论文中适合把它放在第四章“增量视图维护”之后，或移到实现补充/附录，作为降低缓存维护成本的配套快路径，不适合宣称提出了新的热子图缓存框架，也不宜占用一个与主体方法平级的编号小节。

## 6.4 设计二的负载特化一：长传播下的有序执行

### 什么是工作放大

一次真正必要的结果变化，可能因为处理顺序不好而触发多次边扫描。例如 `v` 的距离依次从无穷变成 `100`、再变成 `70`、再变成 `50`，若每次都立刻展开 `v` 的所有出边，它们会被扫描三遍。

这叫工作放大：最终答案相同，但为得到答案做了远多于必要量的工作。

### 基本思想

优先处理距离较小、质量较好的候选，让较差候选暂缓。它与 Dijkstra 和 bucket 方法有相似思想，但论文不应声称发明了这些一般算法；贡献在于把这种距离次序接入当前 affected 删除恢复和 source 闭包，并处理 GPU 队列、去重和成本控制。

### 有序删除如何运行

1. 把 affected 区域的内部依赖转换为局部 outgoing CSR。CSR 可以理解为便于连续遍历邻接的数组格式。
2. 用区域外可靠的边界距离初始化 affected 区域。
3. 从稀疏 active list 中找到最小的 `distance / 128` bucket。
4. 本轮只处理最小 bucket，其他任务保持 pending。
5. 新改善继续入队，直到区域恢复。
6. 发布 affected 距离，并重建相应的 tight parents。

这里的 **tight edge** 指满足 `dist[u] + w(u,v) = dist[v]` 的边，它可以作为当前最短路径的有效见证。

有序删除仍需要 host 逐轮读取 counters，也需要构造局部 CSR，不是完全驻留 GPU 的 persistent kernel。

### 有序插入如何运行

1. 沿用 source 双队列。
2. 找到 pending 工作中的最小距离 `min`。
3. 本轮只服务距离落在 `[min, min + 127]` 的 source。
4. 其余 source carry 到下一队列，等后续窗口再处理。
5. carry 事件和真正改善事件共享 wave ticket，避免重复入队。
6. 整个过程留在 cooperative GPU kernel 中，直到队列为空。

有序插入目前不是完整的物理桶结构，而是每波找最小值，再用距离窗口筛选。

### 适用范围和代价

有序模式主要针对长传播、重复改善严重的工作负载。它会增加每轮最小值搜索、筛选和 carry 的成本，所以不保证所有图都更快，也不保证 wave 数减少。

当前系统通过环境变量 `CG_ORDERED_REPAIR=1` 显式启用，同时选择有序删除和有序插入。系统没有自动识别图类型的选择器。当前证据范围还受限于既定的 1 到 128 正权、有限距离与 ID，以及插入侧 16-bit wave ticket 等条件。

### 可以怎样准确表述创新

> 针对长传播中同一顶点被较差距离反复激活的问题，我们在 affected 删除恢复和插入 source 闭包中引入距离有序服务，使较优候选先扩展、较差候选延后，从而降低重复边松弛造成的工作放大。

论文把它称为**有序影响传播（Ordered Impact Propagation）**。它是影响驱动计算在长传播负载下的主要性能机制，不是第三项与前两项并列的总体系统贡献。

## 6.5 设计二的负载特化二：大批次下的变更复用

大批次的主要问题不同于长传播：当请求很多时，同一批更新可能在 grouping、forward、reverse 和 publication 中被反复转换、复制和排序，CPU 准备成本可能超过 GPU 传播成本。

**批量变更复用（Batched Change Reuse）**利用第四章的统一变更视图来减少这种重复准备：

1. `large` 模式共享一份重型 batch plan，同时保留删除和插入两个阶段的语义视图。
2. 有效变更记录缓冲尽量通过 move 传递，减少重复物化。
3. reverse 复用已有 source 顺序来组织 destination 侧数据。
4. 两个阶段的有序 changed-source 列表可以通过线性 `merge + unique` 合并，避免拼接后重新排序；该 publication merge 当前是显式配置，并非 large 模式必然自动开启。

共享计划不等于合并删除、插入的两个 fixed point。删除恢复仍必须先完成，大批次模式只是复用表示和准备结果，不改变两阶段算法语义。

它也不能被描述为全新的 SSSP 松弛算法，因为主要减少的是 CPU 维护准备。reverse overlay、邻接扫描和重写、内存分配与退休仍有成本，也尚未完成长期 reverse base compaction 和合法 100M 双系统结果。

## 7. 用一个完整小例子串起整个系统

假设当前图中有：

```text
S -> A，距离使得 dist[A] = 2
A -> B，权重 2，因此 dist[B] = 4，parent[B] = A
X -> B，权重 3，而且 dist[X] = 5
B -> C，权重 1，因此 dist[C] = 5，parent[C] = B
```

现在一批更新包含：

```text
删除 A -> B
插入 Y -> Z
```

完整执行过程如下。

1. CPU 按 source 分组，得到删除组 `A` 和插入组 `Y`。
2. GPU 在旧图上发现 `B` 依赖被删边 `A -> B`，而 `C` 又依赖 `B`，所以 affected queue 是 `[B, C]`。
3. CPU 真正删除 `A -> B`，正向邻接和 reverse index 共享同一条有效删除记录。
4. CPU 只为 `B`、`C` 准备入边，不准备全图入边。
5. GPU 检查 `B` 的其他入边，发现仍有 `X -> B`，得到替代距离 `5 + 3 = 8`；然后通过 `B -> C` 把 `C` 恢复为 `9`。
6. 此时删除后的图已经收敛。`X -> B` 虽然不是新增边，它造成的替代路径已经在删除恢复阶段被处理，不会遗漏。
7. CPU 插入 `Y -> Z`，合并 changed sources `[A, Y]`，只发布这两个 source 的 descriptor。
8. 若 `A` 或 `Y` 的邻接已驻留 GPU 且空间足够，则直接修补；所有目标缓存仍有效时，可以跳过常规刷新链。
9. GPU 只松弛新增的 `Y -> Z`。若它改善 `Z`，`Z` 才进入活动队列；否则插入传播立刻结束。
10. 若 `Z` 入队，GPU 展开 `Z` 的出边并持续传播，直到队列为空。

这个例子揭示了系统最关键的逻辑：**旧边带来的替代路径属于删除恢复；新增边带来的改善属于插入传播。先把前者做完，后者才能只从新增边精确启动。**

## 8. CPU 和 GPU 的职责如何划分

| 组件 | 主要职责 | 为什么放这里 |
|---|---|---|
| CPU | 保存完整、权威的图拓扑 | 完整大图放不进 GPU；CPU 内存容量更大 |
| CPU | 按 source 分组并规划更新 | 涉及动态内存、排序、容量规划和复杂结构维护 |
| CPU | 维护 forward 邻接和 reverse index | 它们是权威拓扑及依赖查询结构 |
| CPU | 为 affected 顶点物化 incoming 数组 | 从动态 reverse 结构生成适合 GPU 连续处理的紧凑输入 |
| GPU | 保存顶点距离、parent 等算法状态 | 这些状态规模约与顶点数相关，且被频繁访问 |
| GPU | 识别删除依赖并传播失效 | 大量相似的顶点/边操作适合并行 |
| GPU | 恢复 affected 区域 | 松弛计算并行度高 |
| GPU | 传播插入造成的改善 | 队列式边扩展适合 GPU |
| GPU | 保存热点邻接 | 减少经 PCIe 读取高频数据的代价 |

“CPU 负责拓扑”不等于 CPU 接管最短路传播。当前推荐路径中，CPU propagation owner 默认关闭；CPU 准备结构和依赖数据，主要距离传播仍由 GPU 完成。

## 9. 默认路径、可选模式和当前实现边界

### 默认路径

- CPU owner 容量为 0，主要传播由 GPU 承担。
- 普通删除采用 affected GPU pull，但删除阶段仍有 host 逐轮控制。
- 普通插入采用 block/source cooperative closure。
- reverse 默认单分片。
- publication source merge 默认关闭。
- batch maintenance 默认 `regular`。

### 可选路径

- `CG_ORDERED_REPAIR=1`：显式启用有序删除和有序插入。
- `CG_BATCH_MAINTENANCE=large`：对大批次共享较重的规划数据。
- `CG_BATCH_MAINTENANCE=auto`：当前仅按请求数是否至少为 100 万来选择 large。
- `CG_MERGE_PUBLICATION_SOURCES=1`：显式启用删除、插入发布集合的有序线性合并。
- reverse64：显式选择更多 reverse 分片。

### 尚未解决或没有交付的能力

- 没有通用的 CPU/GPU 自动任务分配器。
- 没有自动判断何时应启用有序模式的图类型选择器。
- 没有跨批次双版本流水。
- 没有长期 reverse base 自动整理机制。
- 没有证明所有算法都同样受益；BFS、CC、PR 目前主要是框架编译兼容。
- 没有证明整个 stored-parent 树在所有情形下都已全面封板。
- 有序删除仍有全顶点 host local 映射初始化，以及局部 CSR 转换、分配和传输成本。
- 普通删除仍有全 `V` reset 和 host 轮间同步。
- 稀疏发布的实际 payload 随 changed sources 变化，但 staging 预留容量仍按最大 batch。

汇报中主动说明这些边界，反而能清楚表明论文知道自己的适用范围，没有把工程结果夸大成普适理论。

## 10. 如何理解已有性能证据

文档中的性能数字都是历史内部比较，本次核对没有重新运行 GPU。不同版本、不同数据集、不同批次数的收益不能相加或相乘，也不能直接当成最终系统相对原版的统一加速比。

| 机制 | 代表性历史结果 | 正确解读 |
|---|---:|---|
| CPU mutation 1→20 workers | TW 827.039→579.388 ms；FS 4734.041→3971.274 ms | 说明并行 mutation 在这两个数据集有收益；EU 完整时间没有改善 |
| large 共享 plan | TW/FS 10M 两批下降 7.36%/9.59% | 开发配对结果，不是全部图上的正式结论 |
| publication 合并 | TW10M 11258.968→10685.928 ms，下降 5.0896% | 证明当前系统内部的显式合并有收益 |
| B5 组合优化 | TW1M/TW10M/FS10M 两批下降 53.52%/29.80%/15.42% | 多项组合证据，不能给每个子项分别重复计算收益 |
| cache patch + gate | 1618.501→594.654 ms，约下降 63.3% | 相对内部 F0-L 基线的一次候选筛查，不是相对 Grapin 原版的正式 cache 消融 |
| 有序删除 | USA/EU100K 80.405→16.492 s / 233.636→36.374 s | 旧版本 deletion-only 对比，当前总开关还同时影响插入 |
| 有序插入 | EU1M 195.076038→42.245784 s，4.62 倍 | 单轮短测，不能扩大成所有数据集或正式十批结论 |

尤其需要避免两类错误：

1. 当前跨系统实验中，22 组共同结果指纹都不匹配，不能据此正式发布“相对原版 Grapin 加速多少”。
2. 显式 memcpy 变少不等于总 PCIe 流量一定同比例下降，因为 Zero-Copy 读取也经过 PCIe，而且当前物理采样证据尚未闭合。

因此，汇报中最好把性能证据称为“机制级内部证据”或“历史配对结果”，不要把它包装成最终、统一、已完整复现的端到端胜出结论。

## 11. 两项总体设计之间的逻辑关系

两项总体设计及其内部机制形成一条逐层缩小工作的路线：

```text
设计一：先限制图结构维护的放大
  source-local 存储 + 有效变更共享
  结果：只维护、只发布真正变化的 source
                         ↓
设计二的核心：再限制计算范围的放大
  affected-only 删除恢复 + successful-relaxation source closure
  结果：只准备必要依赖，只扫描真正活跃的 source
                         ↓
设计二的负载特化：控制必要工作内部的重复
  长传播：距离有序服务 + deferred/carry
  大批次：共享 plan/记录/顺序
  结果：减少重复扩边和重复准备
```

配套缓存机制利用设计一的局部发布信息，直接修补仍应驻留的邻接，减少已有 hot-cache 的维护开销。大批次复用则横跨两章：其数据表示基础属于设计一，在第五章解释如何复用这些表示以减少大批次的重复准备。

所以论文的主线可以概括为：

> 从“拓扑变化范围”和“计算影响范围”两类区域性出发，先减少维护放大，再通过精确恢复、改善传播和负载特化减少计算放大。

## 12. 建议的汇报结构

下面是一套适合 10 到 15 分钟报告的逻辑。重点是先讲问题和正确性约束，再讲机制，不要一开始堆数据结构名称。

### 第 1 页：问题背景

可以这样讲：

> 我们处理的是放不进 GPU 的动态大图。CPU 保存完整拓扑，GPU 保存算法状态并做主要计算。每来一批边的插入和删除，如果重新发布大范围索引、扫描所有顶点，增量计算的优势会被维护和无关工作抵消。

关键词：out-of-memory、streaming graph、CPU topology、GPU computation。

### 第 2 页：核心观察

> 一批更新通常只改变少量 source 的邻接，计算影响也通常局限在部分顶点。但拓扑变化区和结果影响区不是同一个区域，因此需要分别追踪，不能只靠 touched edges 猜测计算范围。

可以画两个不完全重合的圈：一个是 changed sources，一个是 affected vertices。

### 第 3 页：原系统基础与缺口

先承认 Grapin 已有 GPU 增量计算、hot cache 和 Zero-Copy。然后指出三个缺口：

1. PMA 更新可能搬动无关 source，难以安全稀疏发布。
2. 插入从全顶点启动；简单改为新增边启动又会遗漏删除后的替代路径。
3. 长传播中较差距离先扩展，造成重复扫描。

### 第 4 页：总体设计一——更新友好的异构图组织

讲 source-local 邻接、有效变更记录和稀疏 descriptor 发布。强调它是完整契约，而不只是 sparse memcpy。

一句话版本：

> 我们先把一个 source 的更新限制在自己的存储块内，再让 forward、reverse 和 GPU publication 共用同一份实际变更记录，从而安全地只发布 changed sources。

### 第 5 页：总体设计二的核心——恢复与传播

先讲反例：删除旧 parent 边后，替代路径可能来自没有被新增边触发的旧边。然后给出两阶段流程：删除先恢复到不动点，插入才能只用新增边启动。

一句话版本：

> 删除阶段只为 compact affected 集合准备入边并恢复到收敛；插入阶段只让成功改善的 destination 入队，并在 GPU 内完成 source closure。

### 第 6 页：设计一的实现补充——缓存快路径

> 对仍应驻留的 changed source，在 descriptor 发布时直接重写其完整邻接；若目标 resident 集合全部有效，则跳过驱逐、压缩和装载。

明确说这是对 Grapin 原有缓存的维护优化。

### 第 7 页：设计二的负载特化

左侧用距离从 `100 → 70 → 50` 导致三次扩边的例子解释长传播的工作放大，再说明距离窗口让更优候选先执行。右侧说明大 batch 如何共享计划、记录和已有顺序，减少重复物化与排序。

一句话版本：

> 精确队列消除无关顶点；有序执行减少活跃顶点内部的重复扩边；批量变更复用减少大批次中的重复准备。

### 第 8 页：完整流程图

按以下顺序展示：

```text
group batch
→ invalidate on old graph
→ apply deletions
→ materialize affected incoming
→ recover deletion fixed point
→ apply insertions
→ sparse publish and cache patch
→ seed with successful added-edge relaxations
→ GPU closure
```

### 第 9 页：证据与边界

展示最有代表性的机制级结果，同时明确：当前还没有可发布的跨系统统一加速比；ordered mode 需要显式打开，也不是所有图都获益。

### 第 10 页：总结

> 系统的主线不是重新发明 GPU 增量图计算，而是把每批工作的范围逐层收紧：存储只影响 changed sources，删除只恢复 affected vertices，插入只扩展 successful active sources，长传播再通过有序服务减少重复边扫描。

## 13. 一段可以直接使用的口头总述

> 这项工作面向无法完整放入 GPU、并且边持续更新的大图。系统沿用 Grapin 的 CPU 权威拓扑、GPU 增量计算、hot subgraph cache 和 Zero-Copy 基础。我们关注的问题是，原有执行中局部更新仍可能引起较大范围的数据搬移、descriptor 发布和计算扫描。
>
> 第一项总体设计是更新友好的异构图组织。系统在 CPU 端按 source 隔离邻接存储，让一个 source 的扩容不再移动其他 source；同时用一份实际生效的变更记录统一驱动正向邻接、反向索引和 GPU 发布，因此 GPU 只需接收真正变化 source 的 descriptor。对已经驻留 GPU 的邻接，系统还会在发布阶段尝试局部修补，并在目标缓存全部有效时跳过常规的驱逐、压缩和装载流程。
>
> 第二项总体设计是影响驱动的增量图计算。系统先从被删除的依赖边产生紧凑 affected 队列，只为这些顶点准备入边，并在 GPU 上把删除后的结果恢复到不动点。这样就建立了一个关键保证：所有旧边已经稳定，插入阶段只需松弛新增边。只有真正改善距离的 destination 才进入 source 队列，后续传播和收敛检测都在 GPU 内完成，从而避免全顶点启动和无关分区扫描。
>
> 第二项设计还包含两类负载特化。长传播中，一个顶点可能先拿到较差距离并扩边，随后被更好距离再次激活；距离有序服务让较优候选先扩展，以减少重复边松弛。大批次中，系统共享计划、有效记录和已有顺序，以减少 CPU 侧重复准备。两种特化分别针对传播次序和维护准备，不改变前述两阶段语义。
>
> 因此，整项工作以拓扑区域性和结果区域性为主线：更新友好的图组织减少维护放大，影响驱动的增量计算减少计算放大，并用负载特化控制长传播和大批次中的重复工作。它并没有重新提出 GPU 增量计算、热缓存或 Zero-Copy。

## 14. 可能被问到的问题与回答

### 问：为什么不能收到混合批次后一次性算最终状态？

答：因为删除可能破坏旧最短路径，而替代路径可能来自没有变化的旧边。若不先完成删除恢复，只从新增边启动会漏算。当前正确路径明确分成“删除恢复到不动点”和“新增边驱动改善”两个阶段。

### 问：为什么需要 reverse index？有正向邻接不够吗？

答：正向邻接适合从一个已改善顶点向外传播；删除恢复时，要为一个失效顶点寻找所有可能的前驱，因此需要高效查询入边。没有 reverse index，就可能为了找入边扫描全图。

### 问：为什么 source-local 存储是稀疏发布的前提？

答：如果更新一个 source 会搬动其他 source，那么其他 source 的地址也会变化。只发布请求中 touched sources 会让 GPU 保留错误地址。source-local 分配保证未变化 source 地址稳定，稀疏 descriptor patch 才是安全的。

### 问：affected vertices 和 changed sources 有什么区别？

答：changed sources 是邻接结构真正变化的边起点；affected vertices 是最短距离因删除而需要恢复的顶点。前者描述拓扑维护范围，后者描述算法影响范围。一个 changed source 可能影响多跳以外的很多顶点，affected 顶点恢复时也可能读取未变化 source 提供的边界路径。

### 问：为什么插入只需要看新增边？

答：前提是删除后的图已经恢复到不动点。此时所有旧边都不存在未处理的改善，只有新增边能够打破当前稳定状态；某条新增边若成功改善 destination，再由该 destination 的旧出边继续传播即可。

### 问：GPU 队列去重会不会漏掉后来的更优距离？

答：去重只限制同一 wave 内重复调度。同一个顶点在后续 wave 获得更优距离时仍可再次激活。ticket 同时携带 epoch 和 wave，用来区分不同批次与不同传播波次。

### 问：缓存 patch 为什么不是 edge delta patch？

答：当前实现按 changed source 复制该 source 的完整当前邻接。它避免刷新整个 hot cache，但并没有细化到只传输新增或删除的几条边。因此它是 source 粒度的局部修补。

### 问：有序模式为什么不总是默认开启？

答：找最小距离、筛选窗口、carry 未选任务本身都有成本。重复改善严重、传播很长时，这些成本可能换来大量边扫描减少；传播短或工作本来就少时，排序控制可能得不偿失。目前系统也没有自动选择器。

### 问：这项工作相对 Grapin 到底新增了什么？

答：论文层面最稳妥的回答是两项总体设计。第一项是更新友好的异构图组织，包括源隔离布局、统一变更视图和增量 GPU 视图维护；第二项是影响驱动的增量图计算，包括 affected-only 删除恢复、成功改善驱动的精确 source 闭包，以及面向长传播和大批次的执行特化。缓存发布修补是第一项下面的实现补充。

### 问：是否已经证明当前系统全面快于原版？

答：还不能这样声称。现有数字主要是不同阶段的内部机制比较，跨系统矩阵存在结果指纹不一致，当前缺少冻结版本上的完整公平复测。可以报告机制级历史证据，但要保留其版本、数据集和批次范围。

## 15. 最后需要牢牢记住的边界

汇报时最重要的不是多说创新，而是把创新归属说准确：

1. 原系统已经有 GPU 增量计算；当前新增的是更精确的删除恢复与插入执行链。
2. 原系统已经有 GPU hot cache；当前新增的是发布时 source 级修补和有条件跳过维护链。
3. 原系统已经有 Zero-Copy；当前工作没有重新发明 PCIe 映射访问。
4. 原系统的 source 邻接本来就连续；当前新增的是 source 之间的更新隔离和由此成立的稀疏发布契约。
5. 有序执行借鉴一般的距离优先思想；创新点是它与当前删除、插入生产路径的结合及工作放大控制。
6. 两项总体设计是当前论文的贡献组织方式，不代表其中每个组成机制都已证明为全球首次提出。
7. 历史内部收益不能直接拼成最终端到端加速比，也不能替代公平的原版对照实验。

如果只记住一句话，可以记这一句：

> 当前系统在 Grapin 基础上，把动态大图每批更新的工作范围逐层缩小到真正变化的 source、真正受影响的顶点和真正值得优先执行的距离事件，从而减少拓扑搬移、GPU 发布、无关扫描与重复扩边。
