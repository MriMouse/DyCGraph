本报告面向负责编写代码执行计划的 AI。它给出三部分内容：
1. 对 "CPU 计算 owner" 与 "CGgraph-V1.5 式 frontier 切分" 两条路线的**终局性对抗复核**（结论：均判死，附完整证据链与反驳）；

## 第一部分：CPU 计算 owner 路线的终局性复核

### 1.1 证据链（五代独立机制，全部否定）

| 代际 | 机制 | 关键数据 | 失败模式 |
|---|---|---|---|
| B3 (2026-07) | fixed vertex-range destination owner，逐轮回传 | 可见最大 overlap 仅 Wiki/TW/FS `0.308/0.007/0.059 ms` | CPU useful service 微秒级，回传链路税 > 收益 |
| E0-A (2026-07-31) | capacity 0→32 扩容 screening | GPU service 仅变化 `+3.4/+0.5/-1.7 ms`，paper time 全面回退（FS `1536→3176 ms`） | CPU service 增长但**没有替代** GPU source traversal |
| E2/E3 (2026-08) | METIS 域 + 持久 CPU 状态 + changed-source 事件通道 + 异步双执行器 | 通信量降 96–98%，correctness 全过；但端到端仍慢：TW `+5.8%`、FS `+16.0%` vs all-GPU | 即使消除全量 state copy 和 cycle barrier，CPU 可替代服务仍不够覆盖协议固定税 |
| E4-R3-B (2026-08-13) | synthetic 硬件标定 + 解析式 planner | GPU/CPU 边吞吐比 `77.7x`；planner 对三图自然输出 all-GPU | CPU 吞吐不足以缩短 GPU exact-source 关键路径 |
| F1-C (2026-08-20) | SCC condensation 独立子 DAG crossover replay（最后一搏） | 对 CPU 最有利下界仍输：TW `4.514 vs 3.688 ms`（慢 22.4%），FS `44.536 vs 22.770 ms`（慢 95.6%）；R-MAT 快 41% 仅为合成边界 | 真实图 deletion 修复工作量太小，snapshot/mirror/交接成本占优 |

### 1.2 对抗性复核第一轮：Steelman CPU-owner

**最强辩护**：迭代七的对称 replay 显示 20 核 CPU 处理同一 active cohort 只比 GPU 慢 `10.88–21.16x`（保守单 cohort `3.53–7.15x`）。按 CGgraph 的容量公式 `q_cpu = P_cpu/(P_cpu+P_gpu)`，CPU 理应承担 4–8% 的边并等比缩短关键路径。

**反驳（两处断裂，任一即致命）**：
1. **分母消失**。该 headroom 只针对 convergence cohort。R1（exact-source closure）之后，insertion closure 十批累计仅 Wiki `5.6 ms`/TW `2.5 ms`/FS `7.9 ms`，占 paper time `0.15–0.19%`。即使 CPU 把传播全部白拿走，端到端上界不足 0.2%。headroom 的分母（GPU 在传播上花的时间）被自己的 GPU 优化消灭了。
2. **deletion 侧已用最优候选实测**。F1-C 的 replay 条件对 CPU 单方面有利：候选是 `successor_cut_edges=0、dependent_gpu_service_work=0` 的完美独立分量；snapshot 用离线稀疏索引而非生产 D2H；persistent NUMA-aware worker。即便如此两张真实图均 `net_cpu_takeover_gain < 0`。不存在"换个候选/换个数据结构就能赢"的空间——候选已是结构上最好的，而迭代 A 早已证明 CPU 真正的 local closure 只有 18.5 ms/10 batch，贵的是状态准备与交接，这部分不因 CPU 算法变快而消失。

### 1.3 对抗性复核第二轮：实验公平性质疑

**质疑**：是否五次实验都恰好对 CPU 不公平（状态没预热、线程池临时创建、通信没压缩）？

**反驳**：每一项"不公平"都曾被单独修复过，修复后结论不变：
- "每轮临时线程" → E3-B2 换成 persistent worker + lock-free SPSC channel + credit quiescence，仍慢；
- "全量 state gather" → E2-C 换成持久 CPU mirror + 稀疏 reconciliation（batch 通信降到 36–43 KB），仍慢；
- "重复发送未变化 source" → E3-A 换成 changed-source/version 事件（boundary bytes 降 96–98%），仍慢；
- "round barrier" → E3-B2 删除 cycle barrier、只剩 batch 末一次 quiescence，仍慢。
协议税被逐项拆除后，剩下的差距只能由一个不变量解释：**权威算法状态驻留在 GPU，且真实增量修复的工作粒度（每 batch 中位 2.2万–22.4万条受影响入边）比静态协同场景（约 2 亿活跃边）小四个数量级**。这是工作负载的结构性质，不是实现质量问题。

### 1.4 对抗性复核第三轮：剃刀原则

五个机制彼此独立（固定分区 / 图分区域 / 持久状态事件流 / 解析标定 / SCC 独立分量），失败方向完全一致。能同时解释全部证据的最简模型只有一个：

> `可替代的 GPU 关键路径毫秒数（小） < 跨设备状态交接与协议固定税（不可再降的下界）`

任何"再试一个 CPU-owner 变体"的提案，必须先回答：**它在目标 cohort（TW/FS/EU 100k mixed、10 batch）上把哪一段 ≥5% 的 GPU 关键路径毫秒数删掉了**。目前不存在这样的段（deletion GPU closure 每 batch 仅几 ms–几十 ms，insertion closure 接近零）。因此判死成立。

**唯一保留的边界结论**：R-MAT（高 closure、无 cache、67M 顶点）上 CPU 快 41%，作为论文中的 workload crossover 边界讨论保留，不做任何生产实现。

### 1.5 CGgraph-V1.5 移植路线为何不适用（独立小节，供论文写作）

CGgraph 成立的三个前提在本工作负载全部不成立：
1. **工作量前提**：CGgraph 协同轮有数亿活跃边，CPU/GPU 都能连续工作很久；本系统每 batch 修复中位仅 2.2万–22.4万入边，任务寿命毫秒级，切分/合并成本无法摊薄。
2. **结构静止前提**：CGgraph 图结构长期不变，GPU 子图、比例文件（真实图预跑 5 次得 CG_ratio）可复用；动态图每 batch 拓扑都变，比例失效且预跑法本身引入数据集依赖（违反第 0 节纪律）。
3. **状态交换前提**：CGgraph 每轮全量 SSSP state H2D/merge，在静态大轮次下可接受；对小 batch 是致命的（正是 B3/E2 失败的税项）。
可借鉴且已借鉴的只有两点：按 source-edge volume（而非顶点数）计量容量；sink 不参与下一轮 frontier。E1 已冻结这两点，无剩余可移植项。

### P3：强制决策点（依据 P2 数据，二选一或组合，写决策备忘录）

**候选 A：hotness/candidate 的增量维护**。与 cache patch 同构：touched source 的度数变化以 delta 方式更新 hotness 序，而非每 batch 全量 `comp_hotness` + 全量排序。TW 修复前 hotness+candidate ≈ `325 ms/10batch`；若 P2 显示它仍是 ≥10% 大项，此项实现成本低、风险低、且与既有"touched-only"叙事同构。
**候选 B：双版本拓扑流水（原阶段总结的新主线）**。见 P4。
**决策规则**：
- 若 A 的份额 ≥ B 的重叠上界（见 P4 的上界公式），先做 A 再评估 B；
- 若 B 的重叠上界在 ≥2 张真实图 <5%，**B 不立项**（kill criteria），只做 A + mutation 并行化；
- 两者不冲突时可先 A 后 B，分别独立过 gate。

### P4：双版本拓扑流水（若 P3 批准）

**目标**：CPU 构造 next-epoch 拓扑期间，GPU 不空等，继续消费 current-epoch 完成版本无关的工作；反之 GPU 计算期间 CPU 不空等。

**重叠上界（先算再做）**：`gain ≤ Σ_batch Σ_window min(CPU-only span, 相邻可合法重叠的 GPU-only span)`，窗口合法性由 P2 的"读取拓扑版本"列决定。上界须在 ≥2 张真实图 ≥5% 才立项。

**具体重叠窗口（按 P2 数据取舍）**：
- 窗口 A：GPU dependency invalidation 多轮迭代 ∥ CPU reverse-delta 排序 + R2 merge 输入准备（只读 pre-delete 状态）；
- 窗口 B：GPU affected repair closure ∥ CPU addition mutation 的 preflight/COW 块构造（delete-before-add 语义下 addition 本就在 repair 后发布；D3 两遍协议的"只读计划"阶段天然可提前）；
- 窗口 C：GPU hotness（若未被 P3-A 消灭）∥ CPU cache patch staging。

**配套项：touched-source mutation 多核并行化**。source-local chunk store 的 per-source 隔离（C2 已冻结）天然支持无锁并行 mutation；当前 mutation 是主线程串行。这不是线程数微调，而是"隔离性数据结构 → 并行 mutation"的架构推论，直接消费空闲 CPU 多核。设计要点：per-worker arena 避免分配器竞争；preflight 只读可全并行；commit 写互不相交的 chunk；失败原子性沿用 D3 整批 preflight 协议。

**版本协议**：沿用现有 epoch 契约（pending/published + publish-before-traverse stream 顺序），发布仍为一次原子切换；旧版本保留到 GPU reader quiescent，按 touched source 延迟回收（可参考 RadixGraph/NeoGraph 的引用计数回收，但不引入逐边 MVCC、O(V) mirror 或第二份常驻 GPU 拓扑）。

**Gate（沿用阶段总结已定标准）**：TW/FS/EU 至少两图连续 10-batch `paper_algorithm_ms` 交错重复稳定下降 ≥5%；最短路结果、拓扑哈希、版本顺序全部正确；收益必须逐项由"实际被覆盖的等待时间"解释（报告每窗口的 overlap wall）；相同 `--cache` 下 GPU 峰值不高于基线；所有时间计入同一 batch，不做跨 batch 预取（时延语义不变）。

**Kill criteria**：任一图出现正确性回退立即停；若原型在两图 <5% 且无明确可修复的实现税，路线降级为负结果归档，回到 P3-A 收益 + 论文组装。
