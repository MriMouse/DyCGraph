# 2 Background and Motivation

## 2.1 Streaming Graph Processing

A graph $G=(V,E)$ consists of a vertex set $V$ and an edge set $E$ representing relationships between vertices. Many graph algorithms, including breadth-first search (BFS), single-source shortest paths (SSSP), and connected components (CC), iteratively update vertex values by traversing edges from an active work list, adding vertices requiring further processing until convergence [Ligra].

A streaming graph evolves through a continuous sequence of updates, typically grouped into batches of edge insertions and deletions; applying batch $\Delta G_t$ transforms $G_t$ into $G_{t+1}$. Classical systems support efficient topology updates and analytics over the resulting graph versions [STINGER, GraphOne, Terrace]. To maintain up-to-date query results, a straightforward approach reruns the graph algorithm from its initial state after each batch, obtaining $R_{t+1}=\mathcal{A}(G_{t+1})$ even when only a small portion of the topology has changed.

## 2.2 GPU Graph Processing beyond Device Memory

The massive parallelism of GPUs makes them a natural platform for vertex-centric graph processing, where active vertices expose concurrent work through their adjacency lists. Early frameworks map this computation to GPU threads and organize parallel traversal and value propagation [Medusa, CuSha, Gunrock]. However, their scalability is constrained by device memory capacity: large graphs can exceed the memory available on a single GPU, requiring out-of-memory (OOM) processing.

For static graphs, OOM systems retain graph data in host memory and transfer the portions needed for GPU computation. Subway constructs and transfers active subgraphs, EMOGI enables fine-grained zero-copy reads of host-resident edges, and HyTGraph selects between explicit transfers and zero-copy access [Subway, EMOGI, HyTGraph]. CGgraph further combines a reusable GPU-resident subgraph with CPU–GPU task allocation for cooperative execution [CGgraph]. These techniques reduce unnecessary movement, but accessing uncached host data still incurs PCIe communication.

Dynamic graphs add the requirement of maintaining adjacency storage as updates arrive. GPU structures such as Hornet and faimGraph support topology changes within device memory [Hornet, faimGraph]. Extending GPU processing to OOM dynamic graphs requires both access to host-resident topology and efficient maintenance of the GPU view after updates. Unlike static graph storage, the host representation and any GPU-resident adjacency data must remain consistent with the current update batch before dependent computation proceeds. Repeated computation over successive graph versions further increases communication, because the same adjacency lists may be fetched across iterations and update batches. Thus, addressing the capacity limit alone does not eliminate the cost of continuous graph analysis.

## 2.3 Incremental Processing and CPU–GPU Cooperation

Incremental graph processing reuses previous results to avoid recomputing vertices unaffected by an update [KickStarter, GraphBolt, DZiG]. For monotonic path-based algorithms such as BFS and SSSP, a key technique records each vertex's *dependency*: the predecessor that supplied its current value. When an edge deletion breaks a dependency, the algorithm traces dependent vertices, invalidates their values, and repairs them using remaining incoming edges. Inserted edges can introduce better values, which propagate through an active work list until convergence. This confines result maintenance to the affected region, which is often small but can extend beyond the updated edges.

Grapin brings dependency-based incremental computation to GPU streaming graph processing [Grapin]. It maintains dynamic topology in host memory, performs incremental analysis on the GPU, and uses zero-copy access to support graphs exceeding device memory. It also caches frequently accessed subgraphs on the GPU to reduce repeated transfers. Nevertheless, uncached adjacency accesses still traverse PCIe, and repeated accesses during repair and propagation can generate substantial communication overhead. PCIe traffic therefore remains a bottleneck when the working set exceeds the cache. In this execution model, the CPU primarily maintains graph updates and orchestrates GPU execution, leaving its computational capacity available for a larger role in result maintenance. In particular, work that inspects host-resident neighborhoods creates an opportunity to prepare the data needed by affected vertices on the CPU before GPU processing.

CPU–GPU cooperation offers a way to reduce such communication. CGCGraph processes shared graph data on the GPU and assigns snapshot-specific work to the CPU, reducing transfers across concurrent snapshot jobs [CGCGraph]. Related work, POEGA, uses compact proxy graphs and concurrent GPU analysis to reduce OOM accesses across a sequence of snapshots [POEGA]. Both target analysis of multiple available snapshots; their gains rely on sharing or amortizing work across those snapshots. These execution models do not directly address online streaming computation, which must maintain the latest result as each new update batch arrives.

This gap motivates our CPU–GPU cooperative incremental processing of OOM streaming graphs. By coordinating CPU work on host-resident graph data with GPU repair and propagation, we aim to exploit the affected region of each update batch, reduce PCIe traffic, and maintain results without waiting for multiple snapshots to accumulate.
