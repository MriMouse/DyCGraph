\section{Background and Motivation}

\subsection{Background}

\subsubsection{Streaming Graph Processing}

A graph $G=(V,E)$ consists of a vertex set $V$ and an edge set $E$. Graph algorithms such as breadth-first search (BFS), single-source shortest paths (SSSP), and connected components (CC) can be implemented using iterative worklist processing: active vertices update neighboring vertex values and activate vertices for subsequent processing until
convergence~\cite{2013-Ligra}. In batch-based streaming graph processing, topology updates are grouped into batches of edge insertions and deletions. Applying an update batch $\Delta G_t$ to $G_t$ produces $G_{t+1}$, for which a graph algorithm $\mathcal{A}$ computes the analysis result $R_{t+1}=\mathcal{A}(G_{t+1})$. Recomputing results from scratch after each batch can repeat substantial work on unchanged graph regions. Efficient streaming graph processing therefore requires both update-friendly graph representations and incremental maintenance of analysis results.

% \subsubsection{Streaming Graph Representation}

Adjacency-list-based layouts organize neighbors separately for each vertex, enabling localized updates but potentially introducing fragmentation and indirection. CSR instead stores adjacency data contiguously using vertex offsets, providing compact storage and efficient traversal, while topology updates may require costly data movement. Dynamic representations address this trade-off through hierarchical storage, reserved space, or buffered updates. For example, Terrace uses a hierarchical graph container~\cite{2021-Terrace}, Spruce adopts a compact multilevel structure~\cite{2024-Spruce}, and LSMGraph combines an update-friendly LSM-tree with multilevel CSR storage~\cite{2024-LSMGraph}. These designs provide different balances between update cost and neighborhood access efficiency.

\subsubsection{Dynamic Graph Representations}
Dynamic graph representations balance update efficiency, traversal locality, and memory overhead. Adjacency-list-based layouts support localized updates but may incur fragmentation and indirection, whereas CSR provides compact storage and efficient traversal at the cost of potentially expensive data movement during updates. To balance these costs, dynamic
representations employ hierarchical storage, reserved space, or buffered updates, as exemplified by Terrace~\cite{2021-Terrace}, Spruce~\cite{2024-Spruce}, and LSMGraph~\cite{2024-LSMGraph}. A representative space-reserving approach uses a packed memory array (PMA)~\cite{2017-GPMA,2018-pcsr}, which stores adjacency entries in source order with interspersed gaps. The array is divided into hierarchical segments governed by density thresholds. As illustrated in Fig.~\ref{fig:increment-compute}(c), insertions shift nearby entries to consume available gaps. Density violations trigger redistribution within an enclosing segment, while exceeding the top-level capacity threshold triggers array expansion and global redistribution.

% \subsubsection{Incremental Processing}
% Incremental Graph Computation reuses the results of the previous graph snapshot and propagates update-induced changes through the affected dependencies. KickStarter uses dependency tracking and trimming to repair invalidated results~\cite{2017-KickStarter}, while GraphBolt tracks dependencies across intermediate values to support incremental processing with synchronous semantics~\cite{2019-GraphBolt}. For monotonic algorithms such as BFS and SSSP, dependency-memoization records for each vertex the parent through which its result was obtained. A deletion invalidates the results of all vertices that depend on the deleted edge; each invalidated result must then be restored from the remaining incoming edges of the vertex. An insertion can only improve results, and the improvement is propagated along outgoing edges. Figs.~\ref{fig:increment-compute}(a)–(b) illustrate how incremental computation repairs results via dependencies when the graph topology changes.
\subsubsection{Incremental Graph Computation}
Incremental graph computation reuses results from the previous graph snapshot and selectively updates values affected by topology changes. KickStarter uses dependency information to trim unsafe prior values before incremental refinement~\cite{2017-KickStarter}, while GraphBolt tracks dependencies among intermediate values across iterations to preserve bulk-synchronous parallel (BSP) semantics~\cite{2019-GraphBolt}. For path-based algorithms such as BFS and SSSP, a common dependency-tracking approach records a predecessor that supports each reachable vertex's current result. Deleting a recorded dependency edge may invalidate results along the associated dependency paths. Repair involves identifying potentially affected vertices, recomputing their values from valid predecessor results, and propagating subsequent changes. In contrast, an insertion may improve a vertex's result, with any improvement propagated along outgoing edges. Fig.~\ref{fig:increment-compute}(a)--(b) illustrates dependency-based result maintenance under edge insertions and deletions.

Adjacency is transferred either explicitly after the CPU compacts the active subgraph, as in Subway~\cite{2020-Subway}, or on demand through zero-copy access, where GPU threads read pinned host memory with fine-grained PCIe requests, as in EMOGI~\cite{2020-EMOGI}. Grapin extends this model to streaming graphs: it maintains the dynamic topology on the CPU, performs incremental computation on the GPU, and caches the adjacency of frequently accessed vertices in GPU memory as a hot subgraph~\cite{2025-Grapin}. CoIncGraph adopts this execution model, including zero-copy access and hotness-based subgraph caching.

\subsubsection{Out-of-Memory GPU Graph Processing}
Out-of-memory GPU graph processing commonly stores edges in
host memory and retains vertex states and per-vertex adjacency descriptors, which record the location and degree of each source's neighbor list. Static graph systems use explicit transfer of
compacted active edges, as in Subway~\cite{2020-Subway}, or
zero-copy access to mapped pinned host memory, as in
EMOGI~\cite{2020-EMOGI}. For dynamic graphs,
CGCGraph~\cite{2025-CGCGraph} concurrently processes snapshots
by assigning shared data to the GPU and snapshot-specific
data to the CPU, while POEGA~\cite{2026-POEGA} uses proxy
graphs to guide out-of-memory refinement across concurrent
snapshots. Grapin~\cite{2025-Grapin} supports streaming updates
through GPU incremental computation and hot-subgraph caching.
CoIncGraph targets incremental result maintenance across
successive update batches, combining update-local graph
storage with CPU--GPU cooperative repair and propagation.



\subsection{Motivation}
\label{sec:motivation}

Out-of-memory streaming graph processing typically stores graph topology in host memory and vertex results on the GPU, exploiting GPU parallelism and memory bandwidth while fetching adjacency on demand over PCIe. Limited PCIe bandwidth makes adjacency transfers and GPU-side graph-view updates costly. However, streaming updates exhibit \textit{update locality}: a 100K-edge batch modifies the adjacency of only 0.18\% and 0.15\% of sources in Twitter (TW) and Friendster (FS), respectively (Upd.\ in Table~\ref{tab:motivation}). Ideally, graph-view maintenance should scale with changed sources, while computation and adjacency transfers should scale with the affected region. Existing designs, however, lose this locality in both graph maintenance and incremental computation.

\textbf{Graph maintenance amplifies local updates.} Shared-array layouts, such as PMA and CSR, store each source's adjacency contiguously for coalesced GPU access, but insertions may shift, rebalance, or expand regions containing unchanged sources. Because the update batch alone does not identify these relocations, refreshing only updated sources' descriptors risks stale pointers. Existing designs therefore reload all $|V|$ vertex descriptors after each batch, transferring 841\,MB on TW and 1,050\,MB on FS (16 bytes per vertex), although fewer than 0.2\% of sources change (Table~\ref{tab:motivation}). CoIncGraph reduces this volume to about 2\,MB by publishing only changed-source descriptors. Cache maintenance incurs similar overhead: updates invalidate cached adjacency, triggering eviction, compaction, and reloading even when the hot-vertex set remains largely unchanged. Maintenance thus extends beyond changed sources, motivating a graph organization that confines relocation and view maintenance to updated sources.

\textbf{Incremental computation loses update locality.} Repairing an invalidated vertex $v$ requires examining its remaining incoming edges, such as $(x,v)$. However, an unaffected predecessor $x$ remains inactive, and outgoing-edge traversal cannot locate it. Grapin therefore merges deletion repair into insertion processing, reactivating all vertices and scanning vertex states each round to rebuild worklists~\cite{2025-Grapin}. Its initial insertion worklist contains all 52.6M vertices on TW and 65.6M on FS. In contrast, CoIncGraph starts with only the approximately 1.1K and 1.7K destinations improved by inserted edges, respectively (Table~\ref{tab:motivation}). The CPU can supply the incoming adjacency needed to repair invalidated vertices, allowing deletion repair to converge within the affected region before insertions are applied. Insertion propagation can then start only from improved destinations. This motivates CPU--GPU cooperation to decouple deletion repair from insertion propagation and maintain compact worklists throughout. Sections~\ref{sec:graph-organization} and~\ref{sec:incremental-computation} present the corresponding designs.
