日期：2026-09-20。本文是第四章的写作施工稿，尚非论文正文。依据三份指定文档、当前工作树源码和 `3-party-project/paper` 中七篇论文的方法章节整理；实现核对以当前 `hybrid_sssp` 路径为主，包含未提交代码。实验状态采用开发计划顶部最新裁决，不沿用其历史段落中的“下一步”。

## 1. 本章要建立的论点与章节边界

**本章要说明：如何使一次局部拓扑变化，从 CPU 权威邻接的修改，到反向索引维护，再到 GPU 拓扑视图的发布，都具有明确且相互匹配的维护边界。** 重点是这条组合机制为何成立，而非逐项介绍数据结构和优化开关。

沿用既定章名与三节标题：

```text
4  Update-Friendly Heterogeneous Graph Organization
   更新友好的异构图组织
4.1 Source-Isolated Graph Layout / 源隔离图布局
4.2 Unified Change View / 统一变更视图
4.3 Incremental View Maintenance / 增量视图维护
```

三节递进关系为：**源隔离限制物理修改范围；有效变更确定各视图应修改什么；稀疏发布把这些修改安全地交给 GPU。** “更新友好”在章首据此解释，不增加第四个概念性小节。

第二章负责建立拓扑区域性及维护放大的动机，第三章负责说明 CPU/GPU 分工和完整批次流程。本章只用两三句话接续这些前提，不重写背景或架构总览。第五章负责删除影响识别、紧凑 incoming 准备与恢复执行、插入 seed 的完备性、设备内闭包和有序传播。第四章给出这些计算所依赖的图状态与接口，不展开 SSSP 松弛过程。

**贡献归属。** CPU 维护图、GPU 增量计算、连续邻接、pinned memory、Zero-Copy 和 hot-subgraph cache 都已有基础。新增叙述集中在 source 更新隔离、有效变更共享及稀疏发布的组合。尤其不能说原系统每批清空整个 GPU 缓存，也不能把“首次保持邻接连续”写为源隔离布局的贡献。

篇幅目标为双栏正文 **2–2.5 页**，初稿约 1,500–1,850 个英文词，排版后再调整；一幅复合图优先，不堆叠三幅独立架构图。

### 2.1 本章统一采用的段落组织

每节采用“**具体障碍 → 数据对象/操作 → 示例或不变量 → 代价与下一节接口**”，但不机械地把这四个短语写成小标题。段首就说本段解决的技术问题，之后交代动作和因果。

- 使用具体主语：`an adjacency list`、`the reverse index`、`the publication stream`。少用连续的 `framework/mechanism/optimization` 抽象名词。
- 把性质落到可检验的对象：例如“增长一个邻接表不会改变其他 source 的位置”，优于“充分利用区域性，实现高效维护”。
- 首次出现解释 source 是边的起点，避免与 SSSP 的起始顶点混淆；此后统一用 source 或 outgoing adjacency，不反复创造别称。
- 图中用 `u, v, w`，正文就沿用这组符号。每处引图说明读者要看到的差别，不只写“如图所示”。
- 形式化段落限定前提和结论。结构不变量可以解释成立原因；未经证明的运行时间、普遍收益和跨算法正确性不写成 theorem。
- 正文不用研发编号、环境变量、日志 timer 或 C++ 类名组织小节；这些放本文末的证据索引，便于写作核对。

以下英文均为**新写的风格样句**，供落笔时参考，不是参考论文引文：

> A local edge update can change the positions of adjacency lists that the update does not touch. Publishing descriptors only for requested sources is therefore insufficient when updates trigger rebalancing across sources.

> We allocate each outgoing adjacency list independently. When a list outgrows its capacity, only that list moves to a new block; descriptors of unrelated sources remain valid.

> Update requests do not necessarily correspond to changes in the graph. We derive effective deletions from the occurrences found in the authoritative adjacency lists and use the resulting multiplicities to maintain the reverse index.

> The GPU receives one descriptor patch for each source changed in either phase. Dependent traversal waits for publication to complete, while retired blocks are reused only after preceding readers have finished.

避免使用无证据的 `optimal`、`negligible overhead`、`eliminates all redundant work`、`only accesses changed vertices`。论述隔离性质时用明确动词；论述性能时留出测量条件。

## 3. 章首具体怎么写

只写一个短段，完成三个动作：承接第三章的拓扑区域性；指出它不会自动带来局部维护；给出三节的因果链。建议落笔如下，正式正文时与第三章用词统一：

> Topological regionality creates an opportunity to limit graph maintenance to the adjacency lists modified by a batch. This opportunity can be lost when storage relocation affects unrelated lists or when different graph views interpret update requests independently. We organize the graph around source-isolated adjacency blocks (§4.1), derive a unified view of effective changes (§4.2), and use these changes to maintain GPU topology views incrementally (§4.3).

此处不重复定义结果区域性，不展开 SSSP，不列四五项独立贡献，也不预告未经最终验证的加速比。

## 4. §4.1 源隔离图布局：四段完成一个论证

### 第 1 段：指出“只传 touched sources”为何还不够

从原路径的具体耦合写起：原 CPU PMA 已按 source 聚合邻接，但局部插入可能触发跨 source 重平衡。若只更新请求中出现的 source 的 GPU descriptor，被动搬移的其他 source 可能保留旧地址。因此发布范围的收缩必须先有存储层的地址稳定性。

这里比较的是核对文档所指的原系统路径；不能将所有 PMA、所有动态图系统都描述为每次更新必然全局搬移。与 GASgraph 的区别可用一句指出隔离粒度，详细相关工作放相关工作章。

### 第 2 段：定义布局，立即解释图中的一次扩容

定义每个 source `u` 的连续出邻接块 `C(u)`，CPU 保存位置、度数、容量等管理状态，GPU descriptor 用于定位邻接。块位于可映射主存 slab 中；slab 是分配容器，不是图分区或调度 ownership。

示例采用 `u` 容量已满、插入后需换块，`v,w` 无更新。图显示 `u` 迁至新块，`v,w` 的块和位置不变。只说明“邻接容量不足时换块”，不画链表块、不画每条边独立分配，也不暗示每次更新都执行 copy-on-write。

论文可抽象 descriptor 为 `(location, degree)`；实现说明再注明 location 由 slab 与 offset 组成。不要在正文列出全部 ABI 字段。

### 第 3 段：说明修改与并行如何服从同一边界

同一 source 的请求集中规划，删除时匹配现有 occurrence，并计算结果度数与所需容量。容量足够时可原地压紧、追加；不足时分配新块并重写该 source。不同 source 的规划和应用可以并行，容量预检、分配及 epoch/retire 仍有必要串行控制。

在此点出“可见修改前完成所需准备”，具体 reverse Prepare/Commit 留 §4.2；旧块生命周期留 §4.3。不能由 source 间任务独立推出任意 CPU 更新与 GPU 读图都能同时执行。

### 第 4 段：给出隔离性质与成本边界

写作中的性质为：在一个维护阶段中，若 `v` 不属于实际变化的 source 集合，则该阶段不会因其他 source 扩容而改变 `C(v)` 的位置和逻辑内容。成立原因是各 source 使用独立块，重写操作只替换本 source 的块。

紧接着说明：隔离不消除 touched source 内部的删除查找、压紧和扩容复制。即使只有一条更新，触及高出度 source 也可能需要扫描或搬移大量邻接；还存在块容量余量、空闲块和待回收块的空间成本。**不写每批复杂度为 O(更新数)，也不把 source_work 直接当作实测扫描边数。**

结尾引向下一节：位置稳定解决了“哪些邻接可能被连带改变”，但仍需确定请求中哪些变化实际发生。

## 5. §4.2 统一变更视图：五段说明语义和多消费者维护

本节是数据组织的方法主体。顺序固定为“请求与有效变化—共享分组—双向维护—反向表示—发布集合”。

### 第 1 段：最小符号与可执行的更新语义

设批前图为 `G_t`，删除后的中间图为 `G_t^-`，插入后的图为 `G_{t+1}`。记删除/插入请求为 `R^- / R^+`，实际生效的变化为 `Δ^- / Δ^+`。拓扑的边键按当前实现为端点对 `(u,v)`，重数为 `m(u,v)`。

对合法输入中的端点对，有效删除重数为：

```text
k^-(u,v) = min(请求删除次数, 批前存在重数)
m^-(u,v) = m_t(u,v) - k^-(u,v)
m_{t+1}(u,v) = m^-(u,v) + k^+(u,v)
```

当前有效变更记录保存 `source, destination, signed count`。source-local 邻接保存 destination，SSSP 权重在相关路径中由端点规则 `(u+v)%128+1` 计算。因此不能把上述键默默扩成 `(u,v,任意权重)`，不能宣称已支持相同端点不同权重边的独立删除或任意权重更新。固定顶点集合和合法 ID 由输入契约约束。

### 第 2 段：用重数例子解释统一语义

沿用总方案的例子：`Adj(u)=[a,a,b]`，请求删除 `a` 三次、插入 `c` 一次。删除阶段仅发出 `(u,a,-2)`，删后邻接为 `[b]`；在删后计算恢复完成后，插入阶段发出 `(u,c,+1)`，最终为 `[b,c]`。缺失的第三次删除不能进入 reverse，也不能凭空改变边数。

本段后半说明 batch 按 source 稳定分组一次，提供删除和插入两个视图，但分组本身不提前应用插入。**统一的是有效变化的语义来源，不是将两个阶段抵消成最终净变化，也不要求所有消费者共用一份不可修改数组。**

### 第 3 段：说明 phase 内的 Prepare/Apply/Commit 顺序

用明确的生产者和消费者叙述：source 规划确定实际删除、结果度数和有效记录；reverse 根据有效记录完成排序、归约、槽位和内存准备；准备成功后才修改 forward；然后通过不分配内存的 Commit 安装准备好的 reverse 内容。

这是一条阶段内的维护契约：在允许下游消费该阶段拓扑时，forward/reverse 表示相同的边重数。准备失败不能先使 forward 可见图发生部分更新。不要声称整批更新和两次计算具有数据库事务的回滚、隔离或持久性；也不要暗示两个数据结构在每条 CPU 指令之间都同时切换。

### 第 4 段：说明 reverse 为什么采用另一种表示

forward 以 source 为单位，恢复操作需要按 destination 查找当前 incoming，因此 reverse 保存按 source 排序的 incoming base 与 signed overlay。有效变化转换为 destination 视图并归约，查询时合并 base 与 overlay 计算当前重数；当前恢复接口对正重数来源只返回一次，不按 occurrence 重复输出。

此处只解释“表示什么”和“怎样保持最新”。按 affected 队列并行物化、GPU incoming 归约及其性能分析交给 §5.1。承认 overlay 合并可能读取历史记录，当前没有已交付的长期 base compaction；不能说维护只访问本批有效记录。

可用一句不变量收束：在每个可消费的阶段边界，对所有合法 `(u,v)`，forward 中 `u→v` 的重数等于 reverse base＋overlay 表示的重数。当前 `MergeIncoming` 在重数为正时只调用一次 `visitor(src)`，恢复输出本身不保留重复 occurrence。

### 第 5 段：从有效变化导出发布集合

分别定义阶段内实际改变的 source 集 `S^-`、`S^+`，最终发布集合为 `S=S^-∪S^+`。它不是原始请求 source 集，也不是最终邻接差异的最小集合。无效删除不会独自产生 changed source；同一 source 在两个阶段都发生变化时最终只发布一个 descriptor。

再给一个一句话边界例子：先删后加同一条边，即使最终邻接相同，该 source 仍在 `S` 中，因为阶段变化和中间恢复真实发生。不能跨 phase 抵消 `Δ^-` 与 `Δ^+` 后跳过两阶段处理。

共享重型 plan、move 记录缓冲、两个有序 source 列表线性合并的实现与收益放 §5.3.2。本节仅定义其可复用的数据及契约；当前默认发布集合仍是 sort+unique，线性 merge 为显式选项。

## 6. §4.3 增量视图维护：围绕发布完整性和可见性展开

### 第 1 段：解释发布哪些内容以及为什么完备

两个阶段结束后，为每个 `u∈S` 构造一个最终 descriptor patch，并在 GPU 上 scatter 到对应 source 的描述符位置。初始 descriptor 仍覆盖全图，本节说的是每批更新的增量发布。

完备性按两类 source 解释：`u∈S` 获得最终位置/度数；`u∉S` 的邻接和位置由源隔离性质保持稳定，旧 descriptor 仍有效。这样把 §4.1 与 §4.2 的条件明确用于 §4.3，而不是孤立声称“减少传输”。

### 第 2 段：用时序解释安全消费

按当前 SSSP 路径写清下面的先后关系：

1. 批次入口等待既有 GPU 工作完成，回收符合 epoch 条件的旧块。
2. GPU 在旧拓扑上识别删除依赖失效，CPU 应用有效删除并提交 reverse；GPU 使用显式准备的删后 incoming 恢复。
3. CPU 应用插入并提交 reverse，合并 `S^-` 与 `S^+`，暂存最终 patch。
4. 发布 stream 拷贝 patch、scatter descriptor，并完成对应 resident 邻接的修补或失效处理，然后记录 publication event。
5. 依赖这些拓扑数据的消费者等待 publication event，再执行新增边驱动的传播。
6. 被替换的块进入 retire 集合，在后续同步确认相应读者结束后方可复用。

步骤 2 在图中只占一条跨章注记，不展开恢复算法。**删除阶段不发布一份完整 GPU 中间图；不能画成 delete publish → add publish 的对称双发布流水。**

CPU 的 `Publish()` 在排入 GPU 发布操作后推进逻辑 epoch，实际完成由 stream event 和后续同步保障。因此不能把 `IsPublished()` 单独当作 GPU 工作已完成的证明。当前批次入口存在 `cudaDeviceSynchronize()`；不要宣称跨批无阻塞或双版本重叠。

### 第 3 段：区分元数据量与总成本

当前 `TopologyPatchRecord` 的 ABI 为 24 字节，可写：

```text
descriptor payload per batch = 24 × |S| bytes
```

这是实际 source patch 的显式 H2D payload，不含 incoming、缓存完整邻接重写、mapped-host 邻接读取和控制开销。staging 容量仍可能按最大 batch 预留，因此实际 payload 稀疏不等于分配空间为 `24|S|`，更不等于总 PCIe 流量为 O(|S|)。

版本字段用于 CPU 契约检查，当前 scatter 只把编码位置和 degree 写入兼容 GPU descriptor。正文不要画 GPU 每次查邻接都比较版本号的路径。原版全量 descriptor reload 的字节量需按原 ABI 核算，不能用当前 24 字节 patch 大小反推原版每顶点大小。

### 第 4 段：缓存一致性一句必要说明，细节降至附录

主文需保留：受影响的 resident 副本必须修补到当前邻接或标记失效，消费者才能安全使用对应视图。否则只讲 descriptor 正确仍未交代缓存旧内容。

可移附录的实现细节：不增长时复用有效槽位，增长时尝试尾部空间，失败则失效；修补复制的是该 source 的**当前完整邻接**，不是仅复制新增/删除边。refresh gate 判断目标集合及 resident 有效性后，才可能跳过 eviction/compact/load；hotness 计算和排序仍保留。这些不另立方法贡献，也不宣称所有新 kernel 都经过 cache/Zero-Copy 二选一路径。

### 节末：三条性质与第五章接口

用短段总结已建立的三个条件：无关 source 不被动搬移；forward/reverse 在可消费阶段边界重数一致；发布先于依赖读取、块复用晚于读者完成。随后衔接第五章：计算引擎可在删后 incoming 上恢复状态，并在最终发布的拓扑上推进新增边引起的改善。这里不提前证明插入 seed 完备性。
