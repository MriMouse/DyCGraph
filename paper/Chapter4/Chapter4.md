# 4 Update-Friendly Heterogeneous Graph Organization

The regionality in topology changes offers opportunities to reduce maintenance efforts. Conventionally, maintenance can extend beyond the updated edges, as growing an adjacency list may relocate other lists in host memory. Each update must also be reflected in outgoing neighbors, incoming neighbors, and the adjacency locations used by the GPU. We coordinate these changes at the source level. Source isolation keeps unrelated adjacency locations stable (§4.1); a unified change view determines the effective updates and their affected sources (§4.2); sparse publication installs the resulting descriptors (records of adjacency locations and degrees) before GPU consumption (§4.3).

## 4.1 Source-Isolated Graph Layout

The graph is stored in host memory, and GPU descriptors locate its outgoing adjacency lists. The PMA supports contiguous storage within segments while limiting data movement. However, an insertion can trigger rebalancing over a range containing several sources. The resulting relocation changes the GPU indices of lists that were not themselves updated. We aim to minimize such movement and its impact on GPU and other data indices to reduce relocation-related maintenance costs. We therefore isolate allocation and growth by source, limiting publication to sources whose adjacency changes.

Each source $u$ has a contiguous adjacency block and a descriptor recording its location and degree. Blocks are independently allocated within mapped host-memory slabs, which the GPU accesses through the descriptors. Several blocks may occupy one slab, but growing a block does not redistribute its neighbors in the slab. The CPU maintains a separate capacity for each block. When an insertion exceeds this capacity, it allocates a larger block, copies the source's existing adjacency, and appends the new neighbors. Otherwise, the adjacency is updated in place. Figure 2(a) illustrates an expansion of $u$: its location changes, while the blocks and descriptors of $v$ and $w$ remain valid. This preserves the contiguous neighbor access of the original layout while restricting relocation to the updated source.

This organization also provides a natural unit for batch maintenance. The CPU processes requests for each source together, matches deletions against existing edge occurrences, and determines the resulting degree and allocation requirement. Deletions physically remove matched edge occurrences by compacting surviving neighbors once per source, avoiding a separate compaction for every deletion. Additions are appended in the insertion phase. Planning and adjacency mutation can proceed in parallel across sources because their blocks are disjoint. Required allocations complete before visible mutation; allocation bookkeeping and block retirement retain their necessary ordering. The coordination with GPU readers is described in §4.3.

The resulting isolation property is straightforward: an update to $u$ cannot change the adjacency location or contents of another source. This property bounds the scope of physical mutation and will justify sparse descriptor publication. It does not bound mutation cost by the number of requested edges. Deleting from a high-degree source may still scan and compact much of its list, and expansion copies its existing neighbors. Spare block capacity and retired blocks also consume memory. Source isolation removes maintenance caused by unrelated relocations while retaining these costs within the updated lists.

## 4.2 Unified Change View

The forward store, reverse index, and publication path consume different aspects of a batch: outgoing changes by source, incoming changes by destination, and the set of changed sources. We derive all three from one interpretation of the updates. The CPU first groups the requests by source, retaining separate deletion and insertion ranges. This grouping is shared across the two phases, while each phase plans its own mutations against the current forward adjacency. Planning identifies successful deletions, determines the resulting degrees, and emits effective changes as endpoint pairs with signed multiplicities. Thus, reverse maintenance receives changes authorized by the forward store rather than independently matching the original requests.

Consider a source $u$ with neighbors $[a,a,b]$, three requests to delete $(u,a)$, and one request to insert $(u,c)$. Only two deletions succeed, producing $(u,a,-2)$ and leaving $[b]$. Recovery completes on this deletion-stage graph before insertion produces $(u,c,+1)$ and the final list $[b,c]$, as shown in Figure 2(b). The unmatched deletion contributes no reverse change. The two phases preserve the transition $G_t \rightarrow G_t^- \rightarrow G_{t+1}$ even when an edge is deleted and reinserted within the same batch. Such changes cannot be canceled into a net update because recovery consumes $G_t^-$ before $G_{t+1}$ is formed. Section 5 describes the computation on these states.

For reverse access, each destination has an incoming base sorted by source and a signed overlay of multiplicity changes. Effective records are ordered by destination, reduced by endpoint pair, and merged with the corresponding overlays. For large record arrays, stable destination sorting preserves the source order already established during forward preparation, avoiding additional sorting passes over the source key. An incoming query merges the base and overlay to recover the current sources. The representation preserves edge multiplicities, but the recovery interface emits each source once when its multiplicity is positive. This is sufficient for the current SSSP implementation, in which parallel edges with the same endpoints share an endpoint-derived weight. Both overlay maintenance and incoming queries may read accumulated records, so their cost also depends on update history.

Forward and reverse maintenance follow a common preparation boundary. Before changing the forward adjacency, the CPU prepares the replacement overlays, including their ordering, multiplicity reduction, and required storage. Once forward allocations and reverse preparation have succeeded, it applies the adjacency mutations and installs the prepared overlays through allocation-free swaps. Computation proceeds only after both operations finish. At this boundary, forward adjacency and reverse base-plus-overlay represent the same multiplicity for every valid endpoint pair. Preparing the reverse view first prevents a preparation failure from leaving an unmatched forward change. In the large-batch strategy, consumers within each phase also reuse one source plan and transfer the effective-record buffer to reverse preparation, reducing duplicate plans and copies (§5.3.2).

Each phase additionally returns a sorted list of sources whose adjacency actually changed. We denote these sets by $S^-$ and $S^+$ and use $S=S^-\cup S^+$ for final publication. A source with only unsuccessful deletion requests is excluded. A source changed in both phases appears once in $S$, even if its final adjacency equals its initial adjacency. The shared view therefore supplies both the phase-specific topology needed by computation and a complete source set for publishing the final graph.

## 4.3 Sparse GPU Publication and Consistency

After insertions, the CPU prepares one patch for each source in $S$, containing its final adjacency location, degree, and publication metadata. The GPU scatters these patches into the existing descriptor array. This is sufficient to represent the final topology: sources in $S$ receive their final descriptors, while sources outside $S$ retain unchanged adjacency and cannot be relocated by another source's update. Their previous descriptors remain valid. A source updated in place still receives a patch, since its degree may have changed. Publication thus uses the isolation property of §4.1 and the effective-change set of §4.2 to avoid reloading all vertex descriptors. The optional ordered-merge path further reuses the sorted phase lists to construct $S$ in linear time; the default path sorts and deduplicates their concatenation.

Figure 3 shows how publication fits the two computational phases. At the batch boundary, the system waits for preceding GPU work and reclaims eligible retired blocks. Deletion invalidation uses the old state, after which the CPU applies effective deletions and prepares incoming data from the updated reverse view. GPU recovery consumes this data on $G_t^-$ without requiring an intermediate publication of outgoing descriptors. Once recovery finishes, the CPU applies insertions and publishes the final descriptors for $G_{t+1}$. The two phases consequently preserve their graph semantics while requiring only one final descriptor publication.

The publication stream transfers and scatters the patches, repairs or invalidates affected cached adjacency, and records an event. Subsequent topology consumers wait for this event. Cache repair copies the changed source's complete current adjacency into its existing slot when it fits, or reserves unused tail space when the list grows; if space is unavailable, it invalidates the cached copy. This keeps cached neighbors consistent with the published descriptors. Advancing the CPU's logical topology epoch alone does not establish GPU completion: stream ordering and synchronization provide visibility. Similarly, a replaced host block is retired until the relevant readers have completed. These rules support in-place mutation and delayed reuse under the current sequential batch execution.

Each source patch occupies 24 bytes in the implementation, giving a descriptor payload of $24|S|$ bytes per batch. This quantity excludes incoming data, cached adjacency repair, and mapped-host traversal traffic; publication buffers may also reserve capacity for the maximum batch. The reduction concerns descriptor updates for unchanged sources. Together with source isolation and shared effective changes, it allows the computation in Section 5 to recover on the deletion-stage incoming view and propagate insertions on the final published topology without reloading descriptors for unchanged sources.
