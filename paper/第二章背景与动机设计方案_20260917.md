# 第二章背景与动机设计方案

日期：2026-09-17。本文设计第二章的论证结构、问题模型、前序工作组织和动机材料，不直接改写 [background.md](background/background.md)。与[第三至第五章方案](第三至第五章架构与写作方案_20260917.md)配套。

论文定位为面向多种算法的超显存动态图增量计算，SSSP 用作贯穿示例，后续纳入 BFS、CC 等算法。问题模型和设计思想不限定为 SSSP；实现覆盖和实验结论按实际完成情况报告。

## 一、第二章的中心任务与推荐目录

推荐章名：**Background and Motivation / 背景与动机**。

整章围绕一个问题展开：

> 图拓扑和算法结果的变化可能具有局部性，但这种局部性为什么不能自动转化为较小的数据维护与计算开销？

第二章应完成“定义任务→解释局部性机会→说明已有方法→定位剩余挑战”的论证。建议采用四节：

```text
2  Background and Motivation / 背景与动机
   2.1 Streaming Graph Computation / 流式图计算
   2.2 Locality in Graph Updates / 图更新的局部性
   2.3 Out-of-Memory GPU Graph Processing / 超显存 GPU 图处理
   2.4 Research Challenges / 研究挑战
```

四节依次回答：

| 小节 | 读者需要知道什么 | 这一节的结论 |
|---|---|---|
| 2.1 | 图如何变化，计算维护什么，已有增量方法为何能复用结果 | 一批更新需要同时维护图拓扑和算法结果 |
| 2.2 | 拓扑变化与结果变化各自如何局部，两者有什么区别 | 数据维护和计算都有局部性机会，但影响范围不同 |
| 2.3 | 这些工作如何映射到 CPU/GPU，前序系统已经解决了什么 | 已有动态存储、增量计算和数据复用仍需在完整处理链中协调 |
| 2.4 | 局部性在哪些环节被放大，本文要解决什么 | 保持拓扑维护局部性与有效利用结果变化局部性，是两类核心挑战 |

约两页双栏的预算可以是：§2.1 半页，§2.2 半页，§2.3 半页，§2.4 半页；图和引文占用再调整。不要让前序系统的逐项介绍挤占本论文的问题分析。

## 三、2.1 Streaming Graph Computation：先建立通用问题模型

### 3.1 第一段：图更新与查询任务

以边插入和删除为主要更新模型，先使用固定顶点集合：

\[
G_t=(V,E_t),\qquad \Delta G_t=(\Delta E_t^-,\Delta E_t^+),
\]

\[
G_{t+1}=\operatorname{Apply}(G_t,\Delta G_t).
\]

明确 `Apply` 遵循约定的删除、插入和重数语义；涉及重复边时不能简单用普通集合差替代。顶点插删、属性/权重更新只有在确定支持语义后再扩展，不因系统面向多算法就一并承诺。

对算法 \(\mathcal A\)，维护每个快照的结果：

\[
R_t=\mathcal A(G_t),\qquad R_{t+1}=\mathcal A(G_{t+1}).
\]

本文任务是连续批次间复用有效状态、产生每批正确结果；不是同时对任意时间区间内的多份快照执行离线查询。这里不需要展开内部删除后图和发布顺序，它们留到第三章。

### 3.2 第二段：算法状态与迭代模型

采用通用顶点状态 \(x(v)\)、frontier 以及算法定义的更新规则：活动顶点访问邻接、生成候选状态、合并有效变化，直到满足算法的终止条件。依赖信息说明现有状态为何成立，更新可能使其失效。

可以用一张极小的实例化表避免将通用模型写成 SSSP 专用接口：

| 算法实例 | 代表性顶点状态 | 插入可能产生的变化 | 删除可能产生的变化 |
|---|---|---|---|
| SSSP | 从固定根到顶点的距离 | 更短路径 | 原路径失效、替代路径或不可达 |
| BFS | 从固定根到顶点的层数 | 更少跳数 | 原层数依据失效、层数增加或不可达 |
| CC | 规范化的连通分量标签 | 分量合并 | 删除关键连接后分量分裂 |

CC 在正文中必须明确是无向连通分量还是有向图的弱连通分量。标签变化用固定规范，例如分量最小顶点 ID；任意重新编号造成的变化不应被误认为图的语义变化。这里展示模型用途，不声称三种算法的删除恢复实现完全相同。

主文可以用 SSSP 举例解释候选合并；通用叙述用“有效状态变化”。进入第五章的改善驱动传播时，再针对采用的单调合并规则定义“改善”。不把距离减小写成所有图算法共同的性质，也不承诺任意 BSP/非单调算法可直接接入。

### 3.3 第三段：从重计算过渡到已有增量计算

说明重计算从初始状态再次执行整个算法，而增量计算复用仍有效的状态，识别被更新破坏的依赖并修正结果。删除与插入可能具有不同恢复需求。

此处引入前序工作，每类只用一句话服务概念：

- KickStarter：说明依赖信息和 trimmed approximation 如何为复用旧状态提供基础。
- GraphBolt：说明某些算法必须保留同步迭代语义，不能只复用最终状态后继续运行。
- DZiG：说明即使已经增量化，稀疏执行中仍可能存在冗余传播。

这三篇支撑的是“复用状态需要算法语义，增量化也不等于无冗余”。没有必要在这里介绍其完整 API 或各项优化。KickStarter/DZiG 的精确表述沿用现有背景材料作为待核对引文，正式英文稿需回到各自原文确认，不能借 GraphBolt 替它们背书。

**节末过渡句建议：**

> Incremental processing exposes an opportunity to reuse unchanged results. Realizing this opportunity requires understanding both where the graph changes and how these changes affect the computation.

## 四、2.2 Locality in Graph Updates：提出双重局部性观察

这是新第二章的重心。分别定义拓扑局部性和结果局部性，再说明二者不相等，以及现有方法为何分别利用了其中的部分机会。

### 4.1 拓扑变化的局部性

对某次拓扑转换，以 \(S_t\) 表示邻接实际改变的 source 集合。其含义是逻辑上需要更新哪些邻接；物理存储布局则决定实际搬移、重建和发布的范围。

需要区分：更新请求量 \(B_t\)、实际生效更新量 \(U_t\)、邻接发生变化的 source 数 \(|S_t|\)。请求可能无效，也可能多个请求命中同一 source。小 \(|S_t|\) 仍可能涉及高 degree 邻接的大量数据，不能从 source 数直接推出低维护成本。

混合批次中，先删后加可能使最终邻接与旧图相同，却仍经历有效的中间变化；用于评价维护工作的集合应统计相应 phase 的实际 changed sources，并按需要取并集。不要只根据批末净差异认定整批没有拓扑维护需求。

**对应前序工作，放在这一段后：** 动态图存储一直研究更新与扫描之间的折中。例如 STINGER 的 edge blocks、Terrace 的分层邻接组织，以及 Hornet/faimGraph 的 GPU 分块或分页组织。它们说明“让动态图可更新”已有丰富基础；本文接下来关注局部修改能否贯穿双向维护与跨设备视图，而不是宣称此前没有局部存储。

PMA 的 ordered layout/rebalance 可作为物理放大示例。此处只讲现象：逻辑上局部的变化可能改变更大范围的地址或索引。source-local chunk 的解法名称留到第四章。

### 4.2 算法结果变化的局部性

对于顶点结果，定义语义上的变化集合：

\[
C_t=\{v\in V\mid R_{t+1}(v)\not\equiv R_t(v)\}.
\]

\(\equiv\) 表示算法结果的等价关系；对距离可直接比较数值，对 CC 采用约定的规范标签或分区等价。某些更新不改变任何结果，某些只影响局部区域，也可能触发很大范围的变化。

**必须区分三个层次：**

| 集合/范围 | 含义 | 不能混用的原因 |
|---|---|---|
| 最终结果变化集合 \(C_t\) | 两个快照的语义输出差异 | 是事后定义，执行前通常未知 |
| 算法识别的影响范围 | 为安全恢复而识别的依赖失效或潜在受影响顶点 | 可能保守，也可能包含最终值没有改变的顶点 |
| 实际执行访问范围 | 恢复、传播读取的顶点/边及重复次数 | 还包含边界证据、依赖检查和多轮访问 |

SSSP 的某个 parent 被删除后，顶点仍可能找到等长替代路径，因此经历恢复但最终距离不变。混合批次中的删后距离变化也可能被后续插入抵消。所以不能将生产 affected 队列、最终 \(C_t\) 和插入 frontier 视作同一个集合。

### 4.3 用一个小例子同时解释机会与困难

沿用后文的 SSSP 图：

```text
r → u (1), u → v (1), r → x (4), x → v (1), v → z (1)
```

删除 `u→v`：逻辑上只改变 `u` 的出邻接；结果中 `v,z` 的距离分别从 `2,3` 变为 `5,6`。恢复需要读取 `x→v` 和 `x` 的有效状态，即使 `x` 的邻接和最终距离均未变化。

这个例子支持三点：

1. 拓扑变化范围与结果变化范围不同。
2. 恢复局部结果需要访问相关边界，不只是更新端点。
3. 局部性带来复用机会，但需要正确的影响识别和恢复机制。

第二章先讲单次删除即可。第三/第五章再加入无关区域的新增边，解释仅用新增边启动为何不足；同一图分阶段展开，避免重复讲完整算法。

**本节的核心观察建议单独成段：**

> 图更新包含两类可以利用的局部性：实际拓扑变化集中在被修改的邻接上，算法结果的变化由更新对计算依赖的影响决定。二者分别为局部数据维护和增量计算提供机会，但其范围并不一致，也不天然等于系统实际执行的工作范围。

局部性指“变化范围受限”的机会，不要求受影响顶点形成连续内存区域、连通子图或固定 k-hop 邻域。还应指出桥边删除、大批量更新、长依赖链等会扩大影响；这样后续负载特化有自然位置，而不是在第五章突然增加两个特殊模式。

## 五、2.3 Out-of-Memory GPU Graph Processing：围绕处理链组织前序工作

### 5.1 硬件与数据放置，只讲必要事实

一段说明：边数据可能超出显存，CPU 主存提供容量，GPU 提供并行计算和设备带宽；顶点算法状态与部分图数据驻留 GPU，其他邻接通过传输或 mapped-host 访问获得。跨设备访问、GPU 内访问、CPU 拓扑维护是不同成本来源。

不写“GPU 总比 CPU 快”或“CPU 运算能力落后所以必须迁移”的泛化判断。本文优化的是完整批次，瓶颈可以位于 CPU 准备、数据访问或 GPU 传播。

### 5.2 三组方法，分别回答一个问题

**第一组：如何获得本轮所需数据？** 用 Subway 代表活动子图提取，EMOGI 代表细粒度 Zero-Copy，HyTGraph 代表按负载选择传输方式。说明这些设计已利用活动稀疏性，但数据访问方式自身不决定拓扑更新范围，也不保证增量恢复的启动集合完备。

**第二组：如何复用已取得的数据或计算资源？** 用 Liberator 说明跨迭代数据复用，用 CGgraph 说明静态图上复用 GPU 子图及 CPU–GPU 协同计算。强调它们的任务假设，为动态图批次中持续维护视图提出额外要求；不声称它们完全不利用局部性。

**第三组：如何把增量计算与动态图访问结合？** 将 Grapin 作为最直接的基础系统介绍：已有 CPU 动态拓扑、GPU DM 增量计算、热子图及 Zero-Copy。随后提出本文的下一层问题：这些能力具备之后，拓扑更新和算法执行的粒度是否仍可能超出实际变化所需范围？POEGA 可用一句话说明多快照代理图/并发分析的另一条路线，任务边界和离线摄入假设应同时写明。

这一节不展开所有系统优缺点的排行榜。正文引文按篇幅择代表，具体系统差异放 Related Work；对最直接的 Grapin 基础要讲准确、讲充分。

### 5.3 这一节如何收束

建议最后一句：

> 现有方法分别改善了动态存储、增量复用和超显存数据访问，但要使一个更新批次的代价与其有效影响相匹配，仍需协调拓扑修改、跨设备视图维护和增量执行的工作粒度。

这里的“相匹配”是优化目标，不是已经证明的仅依赖 \(|C_t|\) 的复杂度界。

## 六、2.4 Research Challenges：只提出两个主挑战

### 6.1 C1：保持拓扑维护的局部性

英文段首建议：**C1: Preserving Locality in Topology Maintenance.**

逻辑变化局部，实际维护仍可能放大：存储扩容牵动邻近数据；forward/reverse/设备视图重复解释或组织同一批变化；源邻接变化触发较大范围元数据传输或缓存服务。

用一个具体且可追溯的例子落地：本地 Grapin 原版 PMA 更新可能造成跨 source relocation，而其 descriptor reload 复制 `(V+1)` 项。仅将复制改为请求 source 列表不足以保证完备，因为未被请求触及的邻接也可能被搬移。这是原版实现路径的观察，不推广为所有 PMA、所有 GPU 系统的必然行为。

**挑战表述：** 如何让数据布局、有效变更表示和跨设备一致性维护共同保留更新局部性，同时支持 GPU 的高效邻接读取？

对应第四章的三节：源隔离图布局、统一变更视图、增量视图维护。第二章只提出需要满足的性质，不提前列完整实现方案。

### 6.2 C2：把结果局部性转化为完整且有效的增量执行

英文段首建议：**C2: Exploiting Result Locality in Incremental Execution.**

结果变化局部不代表可以只从更新端点出发。删除可能使依赖失效，需要找到未被新增边触发的替代贡献；保守的全点启动保证覆盖，却浪费局部性。即使采用稀疏队列，同一顶点仍可能反复接收更好状态并重复扩边。

用第二章小图说明“局部启动必须有恢复完整性的支撑”。再以本地原版 SSSP 插入侧的 `RebuildWorklist_AllVertices → ExecutePolicy_All` 作为具体执行路径例子，区别于程序启动时的一次性初始化。不要把这个实现事实改写成“原论文没有 GPU 增量算法”。

**挑战表述：** 如何在保留有效状态的同时完整恢复失效结果，并使后续计算由必要的状态变化触发，而不过度扩大启动范围或重复传播？

对应第五章的影响域恢复与改善驱动传播。长传播说明“影响范围局部”和“访问次数较少”是不同问题；大 batch 说明准备/维护开销也可能主导完整批次。这两个负载现象只用一小段引出，不新增 C3/C4 与两章主结构竞争。

大 batch 的主要成本归入 C1 的维护问题，其执行复用技术按既定章节安排在 §5.3.2 解释；不要为了章节对称将 CPU 维护准备误称为算法状态传播。

### 6.3 本章末尾与第三章的连接

建议用以下短段结束：

> 以上分析表明，利用动态图更新的局部性需要同时约束数据维护和增量执行的工作范围。前者要求局部拓扑变化能够在异构数据表示之间被一致地维护，后者要求正确恢复更新影响并由有效状态变化推动计算。下一章据此介绍系统的整体设计。

第三章 §3.1 不再重复文献综述和两个问题的例子，而明确回答：我们依据双重局部性制定哪些原则，以及这些原则如何分别形成第四、第五章。

## 八、局部性观察与瓶颈分析需要什么证据

第二章可以使用概念例子、代码路径事实和少量动机画像，不需要先展示完整性能矩阵。以下是拟用材料，不表示已新增测量。

### 8.1 一张概念图：同一次更新的三种范围

画三层：拓扑实际变化、结果实际变化、恢复所需访问。用颜色区分 `u` 的邻接、`v/z` 的距离变化、`x` 的边界状态。图意是三种范围不相等，不能用嵌套圆暗示它们一定具有包含关系。

如果需要与第三章共用图，第二章先画图和状态变化，第三章只引用并加执行阶段，不重复整张图。

### 8.2 一张小型画像图：局部性与实际工作之间的差距

建议两个面板，选固定且事先确定的输入，用 SSSP 作为示例画像，后续 BFS/CC 实现后补覆盖：

| 面板 | 观测量 | 能支持的结论 |
|---|---|---|
| 拓扑侧 | 请求/有效更新数、phase changed sources、实际修改/搬移字节、descriptor 发布项数 | 逻辑变化范围与实际维护量是否脱节 |
| 计算侧 | 最终结果变化顶点数、删后 affected 数、启动 frontier、扩展次数或处理边数、阶段耗时 | 最终变化、恢复范围和实际执行工作的差异 |

不要把 source 数与 byte 数除在一起当作同一量纲的“放大倍数”。若给出次数放大，应指定同类分母，例如处理边访问次数与对应去重边数；该比值描述重复访问，不等同于理论最优算法的冗余倍数。

最终结果变化集合要由两个已验证快照结果离线比较得到，或由独立分析过程获得；当前 affected/frontier 计数不能替代它。原图删除后又插入的中间状态应单独标注。分析开销不混入正式性能计时。

局部性量化可报告邻接变化 source 比例与结果变化顶点比例，同时报告相关 degree/边量以避免只看顶点数。SSSP 的一组画像可作为动机实例；若要写“跨算法普遍观察”，应补足 BFS/CC 的对应证据。

## 九、第二至第五章的一一对应关系

| 第二章建立的事实/问题 | 第三章设计原则 | 第四、第五章实现位置 |
|---|---|---|
| 拓扑变化与结果变化具有不同的局部性 | 同时利用两种局部性 | 整体架构划分为图组织与增量计算 |
| 邻接局部改变可能带来跨 source 搬移 | 让修改边界服从实际拓扑变化 | §4.1 源隔离图布局 |
| 多视图需要解释同一次真实变化 | 变化语义统一表达 | §4.2 统一变更视图 |
| 设备视图维护可能扩大更新范围 | 基于实际变化维护消费者视图 | §4.3 增量视图维护 |
| 删除恢复需要未改变的边界贡献 | 先完整恢复失效影响 | §5.1 影响域恢复 |
| 保守启动与无效事件浪费结果局部性 | 由有效状态改善推动传播 | §5.2 改善驱动传播 |
| 长传播可能反复扩边，大批次可能重复准备 | 根据负载特征减少重复执行 | §5.3 有序影响传播与批量变更复用 |

正式起草顺序建议：先写 §2.1 的模型与 §2.2 的小图例，再写 C1/C2 确认挑战与方法对应，最后补 §2.3 的必要前序工作。这样引文服务论证，第二章不会再次变成按系统分类的综述。
