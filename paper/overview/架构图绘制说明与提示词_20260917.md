## 2. 模块布局：先画章节，再画方法

建议横向画布，宽高约 1.6–1.8:1。主方法区占约 75%–80%，数据布局插图不超过 15%，余下空间留给输入输出、图例和留白。§4、§5 标题使用论文正式名称，可分两行显示；内部每个组件必须有小节号。

### 上部主框：§5 Impact-Driven Incremental Graph Computation

并排两个主模块：

| 模块 | 内部短标签 | 执行位置及作用 |
|---|---|---|
| **§5.1 Affected-Region Recovery** | `Compact affected queue` → `Affected incoming preparation` → `GPU recovery to convergence` | 三项分别标 `GPU`、`CPU`、`GPU`；失效事件直接形成队列，队列限定入边准备与恢复范围；模块下缘标 `No full-graph state gathering` |
| **§5.2 Improvement-Driven Propagation** | `Added-edge relaxation` → `Improved-vertex queue` → `Exact-source adjacency expansion` | 标 `GPU`；展开产生的成功改善回到队列，用标为 `Device-resident loop` 的回环表示设备内传播与终止；模块下缘标 `No partition-wide scans` |

两者之间画主箭头，标 `Deletion fixed point`。旁边用一行小字说明 `Insert and publish; seed added edges only`：删除恢复先收敛，使旧边不再遗留待传播的距离改善，因而插入只需由新增边启动，无需全点初始化。该箭头表达阶段契约，不代表跳过插入和最终拓扑发布。

视觉重点是紧凑队列限定准备范围、精确源展开及设备内循环。不要将“查旧边”或 reverse index 单独突出为计算创新；不要为去重、ticket 单列模块。删除恢复仍可能有 host 轮间同步，`Device-resident loop` 仅放在 §5.2。

下方放一个较窄的 **§5.3 Workload-Specific Execution** 子框，内含两个并排小框：

- **§5.3.1 Ordered Impact Propagation**，小字 `Distance ordering: fewer rescans`，`GPU` 角标；以细虚线引线连接 §5.1 和 §5.2，表示可选的执行次序。
- **§5.3.2 Batched Change Reuse**，小字 `Shared plans: less preparation`，`CPU` 角标；以细虚线引线连接下部 §4.2。这项属于第五章的执行特化，但优化的是 CPU 拓扑维护准备，不能画成 GPU 松弛算法。

§5.3 内标 `Optional strategies`。虚线引线不带箭头，避免被读成数据传输或固定阶段顺序。

### 下部主框：§4 Update-Friendly Heterogeneous Graph Organization

并排三个方法组件，按章节顺序从左到右：

| 模块 | 内部短标签 | 执行位置及作用 |
|---|---|---|
| **§4.1 Source-Isolated Graph Layout** | `Local adjacency updates` | `CPU`；隔离邻接修改、扩容和搬移的范围 |
| **§4.2 Unified Change View** | `Group requests` / `Effective changes` / `Maintain reverse index` | `CPU`；连接更新请求、实际生效的变化及其多个消费者 |
| **§4.3 Incremental View Maintenance** | `Changed-source patches` / `Publish descriptors` | `CPU → GPU`；图中展示稀疏发布及消费者可见性，不展开配套缓存维护 |

不能把这三个方法画成“4.1 完成后才执行 4.2，再执行 4.3”的单次串行流水。§4.2 的分组用于 §4.1 的局部修改，而有效删除来自 §4.1 对真实邻接的匹配；这种协作在删除、插入两个阶段分别发生。图上将 §4.1 与 §4.2 画成一对短的相反方向箭头，上标 `Grouped requests`（4.2→4.1），下标 `Effective changes`（4.1→4.2）。§4.2 再向 §4.3 供给 `Changed sources`。

### 外部输入输出

主框外侧只放两个小输入框和一个输出框：`Edge update batch` 接入 §4.2；`Previous results` 接入 §5.1；`Updated results` 从 §5.2 输出。图省略初始化和更新文件解析等常规组件，不添加独立 API 层、通用任务调度器或图类型检测器。

## 3. 跨模块接口和小型数据结构插图

### 主接口

除上文局部箭头外，仅保留下面三条跨章接口，标签尽量短：

| 起点 → 终点 | 标签 | 含义 |
|---|---|---|
| §4.2 → §5.1 | `Deletion requests / reverse view` | 删除请求用于旧图依赖失效；reverse 提交后的视图用于 CPU 物化 surviving incoming。两者按不同阶段消费，不表示提前物理删除 |
| §4.2 → §5.2 | `Added-edge seeds` | 删除恢复完成、插入及发布之后，新增边启动传播；不声称直接消费 reverse 的归约数组 |
| §4.3 → §5.2 | `Published topology` | GPU 消费最终已发布的邻接描述符 |

在 §5.2 下缘加一行小字 `GPU expansion reads mapped host adjacency` 即可，不再从插图拉一条穿过全图的 PCIe 虚线。§5.1 内的三个步骤已说明 CPU 准备与 GPU 恢复的边界，不再用两条跨图长线重复表达 affected ID 和 incoming 的往返。

实线箭头只表示数据依赖，虚线无箭头引线只表示策略作用范围。连线不表达所有操作重叠，也不表示一批更新只执行一次拓扑维护。源码中的两阶段顺序由 §3.2 System Workflow 解释；本图取消单独的五步时间轴，腾出空间呈现章节组件。

### 底部小插图：Supporting Data Layout

使用三个紧凑的小组，合计不超过整图面积的 15%，通过对齐和小节号对应上方组件，不再绘制长引线：

1. **§4.1 Host adjacency**：三行小方块，标 `u`、`v`、`w`，行间留出间隙表示独立分配；仅 `u` 行以蓝色突出一次局部变化，其余灰色。无需表示所有边或具体 allocator。
2. **§4.2 Host reverse index**：一条灰色 `Base` 方块条，加一条短蓝色 `Delta` 方块条，表达 base 与有效变化共同确定当前入边。不要画成 GPU 常驻完整 CSC。
3. **§4.3 GPU descriptors**：四个小格，仅一个格着色，表达只发布变化源的 descriptor。小字标 `Sparse patches`。

该插图只说明支撑方法的数据布局，不是第四个大架构层。计算、规划、恢复、发布均画为主图中的操作组件，不能用数组和 Memory 标题代替它们。

## 6. 本轮缓存归属复核（写作依据，不放入图中）

已直接对照原仓库 `C-GpuStreamGraph` 的 `7ffcb29` 与当前实现。原版 `framework.cuh` 已包含 `compute_hot_vertices_sssp`、`confirm_candidate_batch`、`LoadCache`、`evication_cache` 和 `compact_cache`；原版 `hybrid_sssp.cu:266` 起的批次末尾逐项调用上述维护操作。当前仍保留热度统计、排序、候选选择与这些缓存服务。

新增机制集中在两个位置：当前 `csr_graph.cuh:1813` 的容量检查和 `PatchOrInvalidateCachedAdjacency` 在拓扑发布时重写变化源的完整邻接，空间不足时失效；当前 `framework.cuh:1353` 的候选检查结合 `RefreshGate` 决定是否需要执行后续驱逐、压缩和装载，主循环在 `hybrid_sssp.cu:509` 条件调用这些操作。

因此，缓存主体属于复用的基础能力，发布修补与条件刷新属于真实的配套优化，现有证据不支持将其作为本论文新的热缓存架构或独立主贡献。按本轮写作要求，第三章及主架构图省略缓存模块和维护步骤；图标为核心组件与核心流程，不声称穷举运行时全部服务。第四章若需要解释已有视图的一致性，可保留相关实现说明，但不在 Overview 中再次展开。
