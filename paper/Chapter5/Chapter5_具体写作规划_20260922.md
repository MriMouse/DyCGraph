## 一、全章要回答什么，主张什么

保留章名 **5 Impact-Driven Incremental Graph Computation / 影响驱动的增量图计算**；本轮调整内部组织：§5.1 讲高效影响域恢复，§5.2 讲精确与有序传播，§5.3 集中讲配套执行优化。以这一版取代首版“把有序传播与大 batch 并列放在 5.3”的安排。各节之间的因果关系是：

> 更新影响可能只覆盖部分结果，但增量算法的执行仍可能被全图准备、分区扫描和重复传播放大。我们先完成删除后的影响域恢复，为新增边启动建立正确前提；再让实际改善直接决定待扩展的源顶点，在 GPU 内推进传播，并用距离次序抑制长传播中的重复扩边；最后复用批量维护数据、压缩执行管理开销，避免配套维护抵消计算收益。

全章的核心贡献是**让恢复范围、传播粒度和执行次序与实际影响相匹配**。其中，“删除后独立恢复＋新增边启动”必须作为一个正确性闭环；紧凑 affected 数据流、精确 source 执行和设备内闭包解释其性能优势。有序传播是主要的条件性性能机制，大 batch 复用是支撑完整批次效率的维护执行优化。

不要写成“我们提出 GPU 增量计算”“首次利用更新局部性”，也不要把第五章改写成 CPU/GPU 共同执行图算法：当前主路径由 CPU 维护拓扑和准备 incoming，GPU 执行距离恢复与传播，CPU propagation owner 已退出推荐生产路线。

### 章首：用一个问题引出两个阶段

建议两段，不重讲第三章架构。

**第一段：指出执行层的问题。** 依赖追踪能够识别需要修正的状态，但它本身不保证准备、调度和传播的粒度同样小。本地 Grapin 原实现的插入侧仍有 all-vertex worklist 启动和 partition 调度；本项目早期恢复版本还出现全图状态准备税。应分别说明这两个比较来源，不能把内部版本的全部开销归给原系统，更不能写成所有已有增量系统都全图重算。

**第二段：定义阶段并给出解决路线。** 固定顶点集，记批前图为 $G_t$，应用有效删除后的图为 $G^-$，再应用插入得到 $G_{t+1}$。§5.1 先恢复 $G^-$ 的结果；§5.2 先说明插入改善的精确传播，再说明两个阶段如何用距离次序减少重复服务；§5.3 优化同一语义下的配套执行成本。以 SSSP 为贯穿例子，BFS 作为已接入实例简述，不提前宣称 CC 覆盖。

## 四、§5.1 影响域恢复：先讲为什么必须恢复，再讲怎样低成本恢复

### 第 1 段：用替代路径反例说明新增边启动为什么不够

使用一个带具体距离的小图，而不是抽象地说“保证正确性”。例如批前存在：

- $s\to u$ 权重 1，$u\to v$ 权重 1，$v\to z$ 权重 1；
- $s\to x$ 权重 4，$x\to v$ 权重 1。

批前 $d(v)=2,d(z)=3,d(x)=4$。删除 $u\to v$ 后，$v,z$ 的旧依赖失效，但仍可经 $x\to v$ 恢复为 5 和 6。若本批没有插入，或插入发生在不相关区域，新增边 seed 无法激活 $x$。因此只把 $v,z$ 置为无穷并等待插入传播是不够的。

这个例子是算法语义示意，不是直接按当前 SSSP 端点生成权重构造的测试 fixture。无需声称反例或边界补偿思想是我们首次提出；它解释我们为什么把恢复固定点放到插入启动之前。

### 第 2 段：失效事件直接形成恢复集合

**原因：** 若先写 bitmap，再收集全图状态、重建所有分区队列，发现局部影响的收益会被准备成本抵消。

**机制：** 沿批前图的依赖执行失效判定，成功失效直接追加到紧凑队列；失效传播每轮消费该队列新增加的区间，直到没有新失效顶点；随后重置队列内状态。这里保留 parent／tight-edge 防护，不能把算法简化为“从删除端点遍历所有可达顶点”。

**效果：** 同一失效集合贯通识别与恢复准备，避免再通过全图 gather 和全分区 rebuild 找回这些顶点。注意“只消费新增区间”描述的是失效传播，不是普通 pull 恢复每轮只处理新变化顶点。

### 第 3 段：让 incoming 准备跟随 affected，而不是搬回全图状态

**原因：** 出边可以传播失效，却不能主动发现来自未激活外部顶点的替代路径；另一方面，把全图距离搬到 CPU 再修复会引入额外准备和交接。

**机制：** CPU 应用删除并提交第四章的 reverse 视图后，只查询 $A$ 中各 destination 的当前 incoming，形成紧凑 offsets/source 数组，传到 GPU。查询会合并对应行的 sorted base 和 delta；较大集合按 destination 分块并行物化。GPU 距离状态保留原位。

**效果：** 只为恢复所需依赖准备拓扑输入，不需要 GPU 常驻一份完整反向图，也不需要把全图距离交给 CPU repair。CPU 仍保存全图 reverse base，不能写成整个系统没有反向图存储成本。

**这一段需展开的主要性能点。** affected-only 只回答“准备多少行”，还必须回答“每行如何廉价准备”。E4-R2 用有序 base/delta 线性合并替代逐 destination 临时 hash 的构建与查询；B5 进一步把独立 destination 行并行物化到连续输入。与第 4 段的 warp 归约一起，组织成“流式准备—连续传输—协作恢复”的完整服务链，不作为三个碎片名称堆叠。第四章给有序表示，本段给消费该表示时被消除的 hash／串行准备成本；source 次序如何复用到 reverse 维护则归 §5.3.1。

与第四章的界面要清楚：第四章讲 incoming 如何保持正确，第五章讲为何仅请求这些 incoming、它们如何驱动状态恢复。这里不重讲 signed multiplicity 例子。

### 第 4 段：边界初始化与 affected 内固定点

**机制：** 失效状态从无穷开始；对 $v\in A$，从当前 incoming 读取前驱距离，计算替代候选，并反复更新直至无变化。$A$ 外仍正确的有限距离提供边界值，$A$ 内的改善继续影响后续恢复。普通 GPU 路径由 warp 合作归约一行 incoming。

**为何这个实现点值得讲。** 大 incoming 行若由单线程串行归约，即使 affected 不多，恢复仍可能很慢；warp 分担一行读取并合作归约候选，降低行内串行服务成本。这是实现完整恢复链的重要部分，B5 有组合收益证据；不能把它与 parent CAS、ticket 等纯正确性支撑混在一起，也不能把 B5 全部降幅独立归给 warp。tile=4096、lane/shuffle 等细节不进主段落。

可以给一个统一松弛式：

\[
d(v)\leftarrow\min\left(d(v),\min_{u\in\operatorname{Pred}_{G^-}(v)}[d(u)+w(u,v)]\right),\quad v\in A.
\]

随后用短段说明充分条件：若失效识别覆盖所有需要重置的状态，且 $A$ 外保留的距离正确，删除后仍存在的路径可由有效边界进入 $A$ 并通过内部传播恢复；没有可达边界的顶点保持无穷。对正权 SSSP／单位权 BFS，收敛得到删后距离，插入阶段不再需要弥补旧边上的遗漏改善。

不要只用“满足 Bellman 不等式”替代完整正确性论证；距离必须由实际路径支持。stored-parent 的全模式保证仍需要单独核对，不能由最终 distance checksum 相同推出。

### 第 5 段：把省下的工作与剩余成本说准确

恢复所需 incoming 数记为 $M_A$；它包含来自 $A$ 外的边界依赖，不能只数 $A$ 内部边。当前 reverse 会将仍存在的同一 source–destination 多重边归并为一个来源；此处成立依赖当前相同端点使用相同边权的语义，不直接推广到任意不同权重的平行边。

紧凑输出规模为 $O(|A|+M_A)$，但 CPU 查询实际扫描对应的 base 条目与 overlay，可能大于输出。普通 pull 经过 $R$ 轮还可能反复扫描这些 incoming，工作量可达 $O(R(|A|+M_A))$；全批次另外仍有全 $V$ reset、hotness 等工作。因此只声称“缩小恢复准备和计算范围”，不声称整批 $O(|A|)$ 或只访问结果最终变化的顶点。这一剩余重复扫描自然引出 §5.2.3。

## 五、§5.2 改善驱动传播：从正确的局部启动走到精确执行

### §5.2.1 局部启动与精确活动源

**第 1 段：先证明为什么新增边是完备启动来源**

§5.1 已得到 $G^-$ 的正确距离；插入并发布最终拓扑后，只扫描本批新增边。如果出现更短路径，该路径必含新增边，否则它在 $G^-$ 中已经存在。取该路径上的第一条新增边，其前缀全由旧边组成，已由删后距离覆盖；松弛新增边及后续邻接即可传播新的改善。后续路径即使包含更多新增边，也可在最终图的正常扩展中访问。

这段紧接 §5.1，是全章最重要的逻辑连接。应称“新增边松弛产生 seed”，不能写成“所有新增边的端点都入队”。不可达 source 或不能改善目标状态的新增边不产生有效启动工作。

**第 2 段：把成功更新变成下一波的 source**

**原因：** 以分区为执行单元时，一个顶点改善仍可能带动不相关顶点／邻接的检查。

**机制：** 新增边或扩边松弛成功后，destination 直接成为待展开 source；服务该 source 时检查并提交最新改善，再按第四章的 descriptor 读取它的真实出邻接。新成功的改善继续形成下一波。

**效果：** 从“改善事件”到“邻接展开”形成直接通路，不需要把事件重新扩大成整分区工作。这里的精确性是 source 粒度，不意味着每条被扫描的边都成功松弛，也不意味着每个 source 全批只访问一次。

当前主路径以一个 block 服务一个 source。这个映射只需一句实现说明：CTA／warp 和 vertex-centric 调度已有大量先例，不把该映射本身认领为新算法。当前 closure 通过 `graph.edge_dest` 读取 mapped source 邻接，不应顺手声称它自动获得 GPU hot-cache 命中收益。

### §5.2.2 设备内闭包与工作保持

**第 3 段：设备内推进闭包，减少小 frontier 的控制开销**

**原因：** 工作已经缩小后，每波 host frontier 构造、计数回读与再次启动可能成为显著开销。

**机制：** 使用两条 GPU 队列，cooperative kernel 完成本波展开、跨 block 同步、队列交换和空队列检测；host 在闭包结束后取得完成状态与统计。

**效果：** 插入闭包不再需要 host 逐波协调。这里仍有 `grid.sync`，不能写“无同步”或“完全异步”；删除失效／普通恢复仍由 host 控制轮次，不能把插入性质扩展到整个批次。

**第 4 段：用一小段解释去重为什么不会丢工作**

多个前驱可能同时改善同一目标；若同一波重复服务该 source，会增加工作并引发状态提交竞态。波次 ticket 合并本波的入队请求，但后续波的更优改善仍可重新激活；服务时使用最新 buffer，不把第一次入队时的旧值当作永久任务值。

正确性说明应覆盖：成功改善有待服务机会；同波合并不阻止以后再激活；本波所有生产者完成后才交换／判断队列；队列和票据范围合法。ticket 是正确性支撑，不安排“关闭去重”的错误性能对照，也不宣称已有它独立带来的主要加速比。

**第 5 段：用工作量表达收益，连接有序传播**

插入实际扩边量可用

\[
W_{\mathrm{expand}}=\sum_k\sum_{u\in X_k}\deg^+_{G_{t+1}}(u),\qquad X_k\subseteq Q_k
\]

解释，其中 $X_k$ 是该波确实提交改善并展开的 source；有序模式中 carry 项不属于本波 $X_k$。精确执行消除与 $X_k$ 无关的分区跨度，但同一 source 仍可能在多波出现。**“范围已经精确，次数仍可放大”**就是 §5.2.3 的入口。正文篇幅不足时公式改为一句话，定义保留在实验工作量说明中。

### §5.2.3 有序影响传播

本段跨接两种传播：§5.1 的恢复内部传播与 §5.2 的插入传播。恢复已在前文定义，现在集中解释共同的重复工作问题和两种实际有序执行器；不是把删除恢复改到插入之后，也不把有序删除遗漏在插入叙述中。

**第 1 段——问题和例子。** 精确 frontier 无法阻止某顶点先收到“跳数少但权重大”的路径，再收到“跳数多但权重小”的路径。若较差距离已经向下游传播，较好距离到达时就要重新扩边。在存在长传播链的负载上，这类重复工作可能成为主导项。“大直径”是常见场景，不是每个大直径图都会受益的充分条件。

**第 2 段——有序删除。** 普通 affected pull 多轮扫描 incoming；有序路径把 affected 内部依赖转为局部 outgoing CSR，用外部边界距离初始化 pending 集合，选择最小非空距离 bucket，展开选中工作，保留 deferred 工作。将传播由反复检查所有恢复行转为服务 pending 源。

**第 3 段——有序插入。** 保留 §5.2 的设备内双队列，扫描 pending buffer 的最小距离 $m$，优先服务窗口 $[m,m+127]$，其余 carry 到后续波。未选任务不提前提交 value，carry 与改善事件共享去重，后续读取最新 buffer。

两种模式只在“优先传播较小距离”上统一：删除用 $\lfloor d/128\rfloor$ bucket，插入用动态最小值窗口，不能画成同一物理 bucket 队列。当前 SSSP 权重为端点确定的 1–128 正整数；BFS 特化为 1。固定 128 是当前实现选择，不宣称任意权重下的最优宽度，也不将其写成标准 delta-stepping 的完整实现。

**第 4 段——收益与代价。** 收益是可能减少重复边扫描，而不必减少 wave 数。代价包括 local CSR 构造与复制、全 $V$ 的 host local-ID 映射初始化、bucket／窗口选择、pending/carry 管理，以及有序删除的 host 计数回读。社会图上的宽 frontier 或短传播可能不足以摊销这些成本。

本段末说明显式选择规则。`CG_ORDERED_REPAIR=1` 当前联动有序删除和插入，不是自动检测图直径；代码另有显式 insertion schedule 入口，但论文现有整组 mode 结果不能直接拆成两个单项收益。9 月 22 日实验整理还记录 FS ordered 路径存在 `invalid configuration argument` 失败，不能把所有图和模式写成已完成验收。

## 六、§5.3 配套执行优化：按被消除的成本归组

推荐标题 **Supporting Execution Optimizations / 配套执行优化**。这一节容纳不需要改变恢复与传播语义、但值得交代的性能实现，分为“批量维护—执行资源—条件性维护”三组。不要按 I 编号、数据结构名字或开关数量组织。

“配套”不等于收益小：reverse64 和 cache gate 在特定历史输入上收益很大，但分别是维护路径的实现特化、继承缓存上的维护改进，且证据范围有限；它们应有明确位置，而不另立增量图算法贡献。

### §5.3.1 批量维护中的共享、顺序复用与并行组织

**原因。** 恢复与传播缩小以后，大批次的 grouping、plan、有效记录复制、reverse 槽位创建及发布集合排序可能成为主导成本。第四章定义共享的表示及正确性契约，本段解释如何低成本地执行这些维护。

**机制。** 用两段叙述同一条“变更准备→多视图消费”链：

1. **少构造、少复制、少重排。** mixed batch 只分组一次；phase-active 索引让各 phase 只处理自身有工作的 source。保留的稳定串行 radix 降低大列表分组成本，不能与后来被否决的并行 radix 混为一谈。large 路径共享重型 source plan、用 phase 索引访问结果，并移动有效记录缓冲给 reverse 消费。有效记录已有 source 次序时，只补 destination 稳定排序；两 phase 的有序 changed-source 集合可显式 merge+unique，避免拼接后重排。
2. **把独立维护工作并行化。** source prepare／compact／rewrite 由持久 worker 池分发；reverse 按 destination 预建槽位后并行合并独立 overlay。显式 destination-range 分片进一步分散单 map reserve／insert／rehash 的串行成本。保留必要的 allocation、提交与回收次序，不把 CPU 维护并行写成 CPU/GPU 图算法共同传播。

**效果。** 前一组减少重复表示与排序，后一组减少必需维护的串行时间；不能把它们统称为“少访问边”。reverse64 历史 FS1M 同版本十批完整下降约 42.0%，TW100K 基本持平，说明它值得保留但并非通用收益。source 1→20 workers 的 TW／FS 收益是资源消融，不是新的算法加速比。

**正文粒度。** 两段主文覆盖上述两类成本即可；radix pass 数、worker grain、分片数及配置表移到实现说明。本节仍明确 regular 默认、large 显式、auto 按请求总量 ≥1M 选择；reverse64 与 publication merge 是独立配置，不能写成 large 必然启用的组件。phase-active 单项未证明稳定收益，不分配独立数值。

### §5.3.2 执行控制与临时资源复用

**原因。** 必要工作已经被限定后，重复创建队列／工作区、额外中间队列和多次控制回读仍可能影响短服务的成本。

**机制。** 有序删除在设备侧合并控制步骤，复用 selected／deferred 队列存储并保持 pending 工作；恢复 incoming 工作区按需扩容后保留；publication staging 和 events 预留／复用，并接入已有完成边界。这里只解释资源与控制开销，发布可见性协议继续引用第四章。

**效果。** 减少额外控制往返、临时数组和重复分配。有序删除控制／队列优化的 EU／USA 完整 service replay 曾下降 11.6%／8.1%，GPU 空间减少 79.1／47.5 MiB；这是 replay service 的证据，不是生产整批 P0。工作区复用没有独立显著收益证据时只作一句实现说明。

ticket、parent/tight-edge 防护、epoch 生命周期是正确性条件，分别留在 §5.1、§5.2 或第四章解释，不为满足“次要优化进 5.3”而挪走必要前提，也不包装成独立加速。

### §5.3.3 条件性缓存维护

**原因。** 即使传播工作很少，touched source 的缓存失效仍可能启动整条 eviction／compact／load，使维护成本掩盖计算收益。

**机制。** 引用第四章的 source 邻接发布修补：槽位可用时更新当前完整邻接，增长时尝试尾部空间，失败则失效并走正确回退；随后确认目标 resident 集合和 payload 有效，满足 gate 才跳过常规缓存维护链。

**效果。** 降低无需更换有效缓存时的维护成本。历史 TW 十批内部 F0-L 中位基线→单次候选，完整时间下降约 63.3%，因此不能从收益防漏表中删除；但这不是相对原版首次获得缓存复用，也未证明最终版普适收益。全顶点 hotness／候选排序仍在，不能说实现了事件式增量热度维护。

**与第四章分工。** 第四章解释修补和 gate 如何保持图视图正确；第五章只用一个短段说明何时跳过维护、为什么保护完整批次收益，不重讲缓存布局和分配。也不声称 exact-source kernel 因这一机制获得 cache-hit 加速，它目前读取 mapped source 邻接。

## 七、一个主算法框与一幅机制图

### Algorithm 1：恢复与传播的完整接口

建议放在 §5.2，约 20 行。下面是语义级草案，不是源代码逐行翻译：

```text
ProcessBatch(G_t, state, deletions, additions):
    P ← PrepareBatch(deletions, additions)                 // §4
    A ← InvalidateDependencies(G_t, state, deletions)
    ResetInvalidatedStates(A)
    ApplyDeletionsAndCommitReverse(P)                     // §4
    incoming ← MaterializeCurrentIncoming(A)
    RecoverToFixedPoint(A, incoming, state)               // §5.1
    ApplyInsertionsAndCommitReverse(P)                    // §4
    PublishFinalTopology(P)                              // §4
    Q ← RelaxAddedEdgesAndEnqueueImprovements(additions)
    DeviceClosure(Q):                                    // §5.2
        while pending work exists:
            Qnext ← empty
            for each source u selected from Q:
                if CommitLatestImprovement(u):
                    for each (u, v) in final outgoing adjacency:
                        if Relax(u, v) succeeds:
                            EnqueueOnceForNextWave(v, Qnext)
            retain any deferred work in Qnext            // ordered only
            synchronize producers; swap(Q, Qnext)
    MaintainCacheIfRequired()                            // §4 / 实现
```

删除依赖失效在旧图上进行；恢复读删除后的 incoming；插入传播在最终 publication 完成后读出邻接。伪代码不插入“删除阶段发布全量 GPU descriptor”，不引入尚未交付的跨批流水线。ordered 的 selected/deferred 细节在 §5.2.3 解释，普通模式选择全部 pending 工作。

## 十一、与已有章节需要同步的事项

本次只新增本规划，不直接改动已有章节；正式写第五章时建议同步处理下列文字。

1. **Overview 的比较对象。** 当前 “Prior work on incremental graph computation initializes worklists over all vertices” 过于宽泛。建议限定为所比较的 Grapin 实现路径；全图 state gathering 另标明是本项目早期恢复实现的开销，不混为一种基线。
2. **Chapter4 的 reverse compaction。** 当前正文称 delta 在周期性异步 merge 中并入 base，但同文件图注、真实性核对与本次代码均不支持已交付该机制。应删除这一承诺，说明 base 与累积 delta 合并读取；第五章不依赖周期性后台整理。
3. **背景的版本。** `background.md` 仍以 CPU 计算能力未利用引出协同方向，与当前主路径不一致；以 `background_rewritten_20260917.md` 的区域性与工作放大主线衔接更合适。不要让第五章承接已退出的 CPU propagation 目标。

5. **实际语义。** 本文支持固定顶点集上的批量边更新；当前 SSSP 边权由端点生成，不能写成已验证任意输入权重或任意带权多重图。实验设置应明确这个契约。

## 十二、按什么顺序开始写正文

先写 §5.1 的替代路径例子与 §5.2 第一段的新增边完备性，形成连续因果链；再写 compact affected→incoming→GPU repair 与成功事件→source queue→设备内闭包两条数据流。随后补 §5.2.3 的重复工作例子、两种实际次序及成本，最后将批量维护、执行资源复用与条件性缓存维护写成 §5.3 的三组配套优化。
